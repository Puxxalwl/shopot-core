# CORE-API — бинарный интерфейс ядра shopot

Техническая спецификация для авторов GUI-клиентов. Английская версия:
[../CORE-API.md](../CORE-API.md).

Ядро (демон `shopot serve`) владеет криптографией, контактами, сессиями и
доставкой. Клиент подключается по unix domain socket и рендерит. Протокол
**бинарный**: никаких строк-как-протокола, JSON и человекотекста на проводе
— только типизированные байтовые кадры и машинные коды (методы, статусы,
события).

- Версия API: **2.2.0** (возвращается `GET_VERSION`, semver). История:
  2.0.0 — хвост entities в payload'ах сообщений (§4.3); 2.1.0 —
  `SEARCH_MESSAGE`/`GLOBAL_SEARCH_MESSAGE` (§4.3); 2.2.0 — закрепления и
  удаление чатов, закрепление сообщений, пересылка визитки (§4.8),
  событие `CONTACT_CARD`, честный бит `delivered` (§7).
- Нормативный провод-протокол: [../PROTOCOL.md](../PROTOCOL.md).

## 1. Модель

| Сущность | Определение |
|---|---|
| ядро | процесс `shopot serve`. Один пользователь = один демон = один `$HOME`; несколько пользователей на машине — разные `$HOME` |
| клиент | любой процесс, подключённый к `$HOME/.shopot/api.sock` (UDS, права 0700). Параллельные соединения разрешены; события рассылаются всем |
| контакт | собеседник, идентифицируется bundle (`enc_pk‖sign_pk`, 64 байта). В API контакт — целочисленный `cid` (u32), стабильный в рамках `$HOME`: 1..N в порядке добавления |
| msg_id | 16 случайных байт, глобально идентифицирует сообщение; по нему реакции, статусы, `GET_MESSAGE` |

У ядра нет TUI/CLI: демон не имеет интерактивного ввода, всё управление
идёт через это API.

### Максимум одно действие пользователя

Ядро берёт на себя: знакомство (протокол JOIN), поиск адреса
(LAN-мультикаст, автодозвон), доставку офлайн (outbox + ACK),
переподключение, presence. Для пользователя любой сценарий — ноль или одно
действие (вставить инвайт-код). Клиент не должен просить подтверждений,
адресов и порядка действий — ядро уже всё решил.

### Чего ядро НЕ делает

- UI/рендер/эмодзи-глифы, QR — клиент.
- Хранение на сторонних сервисах — их нет; контент живёт только на двух
  устройствах (шифрованный лог локален).
- NAT-обход для двух сторон за NAT: канал — LAN, прямой TCP (авто-выбор
  порта из диапазона 7777–7786) или релей (`shopot relay` на любом
  сервере).
- Разбор картинок/файлов: байты передаются как есть.

## 2. Кадр

Все целые — little-endian. Заголовок любого кадра — ровно 16 байт:

| Поле | Тип | Смещение | Значение |
|---|---|---|---|
| magic | u16 | 0..2 | `0x5A50` («ZP») |
| version | u8 | 2 | `1` |
| kind | u8 | 3 | `1` = REQUEST, `2` = RESPONSE, `3` = EVENT |
| id | u16 | 4..6 | метод (REQUEST/RESPONSE) или событие (EVENT) |
| request_id | u32 | 6..10 | корреляция: ставит клиент, ядро повторяет в RESPONSE; у EVENT = 0 |
| status | u16 | 10..12 | код статуса (только RESPONSE; иначе `0`) |
| payload_len | u32 | 12..16 | длина payload, `0..1048576` (1 МиБ) |

- Один REQUEST = ровно один RESPONSE с теми же `id` и `request_id`.
- Payload больше 1 МиБ → `TOO_BIG`, соединение закрывается.
- Сломанная магия/версия или не-REQUEST кадр от клиента → `BAD_FRAME`,
  соединение закрывается (ресинхронизация потока невозможна).
- Текстовых полей нет. Строки — это `str16` = `[len u16][байты]` и
  `str32` = `[len u32][байты]` (сырые UTF-8 байты, без терминатора).
- Лишние/недостающие байты в payload метода = `BAD_FRAME` (строгий разбор).
- `CLOSE` закрывает соединение (не демон).

## 3. Коды статуса

Имена — контракт. Человекотекста в ответах нет и не будет.

| Код | Имя | Когда |
|---|---|---|
| 0 | `OK` | успех |
| 1 | `BAD_FRAME` | кадр/payload не разобран (магия, версия, длина, структура) |
| 2 | `UNKNOWN_METHOD` | неизвестный id метода |
| 3 | `BAD_ARGS` | неверные/неполные значения аргументов |
| 4 | `NO_CONTACT` | cid не существует |
| 5 | `CONTACT_BLOCKED` | контакт заблокирован локально |
| 6 | `NOT_FOUND` | объект не найден (сообщение по msg_id) |
| 7 | `TOO_BIG` | превышен лимит размера (тело, аватар, кадр, история) |
| 8 | `BAD_INVITE_CODE` | инвайт-код не разобран/не распознан |
| 9 | `TOO_MANY_INVITES` | реестр приглашений полон (4 живых) |
| 10 | `FILE_NOT_FOUND` | файл по пути не найден/не читается |
| 11 | `UNSUPPORTED_REACTION` | codepoint вне U+0000..U+10FFFF |
| 12 | `NO_SESSION` | нет живой сессии с контактом (нужна для операции) |
| 13 | `BUSY` | линия занята (звонок уже идёт) |
| 14 | `NO_CALL` | активного звонка нет |
| 15 | `NO_RELAY` | релей недоступен |
| 16 | `TRANSPORT_FAILED` | транспорт не поднялся (dial/рукопожатие) |
| 255 | `INTERNAL` | внутренняя ошибка ядра |

## 4. Методы (REQUEST)

Имена — контракт, значения стабильны. «∅» — пустой payload.

### 4.1 Служебные

| Метод | id | Payload | Ответ (payload при OK) |
|---|---|---|---|
| `GET_VERSION` | 2 | ∅ | `[major u16][minor u16][patch u16]` |
| `GET_IDENTITY` | 3 | ∅ | `[bundle 64][fingerprint 32]` — BLAKE2s-256(bundle), сырые байты |
| `CLOSE` | 1 | ∅ | ∅, затем ядро закрывает соединение |

`GET_VERSION` — проба готовности: подключились → `GET_VERSION` → работаете.
Рост Major = контракт этого документа менялся (см. CHANGELOG).

### 4.2 Контакты

#### `CREATE_INVITE` (4)
Payload: `[flags u8 (бит0 = relay)][name str16 ≤ 32][addr str16]`.
- Пустое name → `shopot`. `addr` — `host:port` (опционально: иначе держатель
  найдёт приглашающего по LAN-анонсу). `relay=1` требует `addr`;
  подключение пойдёт через релей — пир не видит ваш IP.
- Секрет одноразовый: гасится первым валидным JOIN. Реестр: до 4 живых
  приглашений в памяти демона (рестарт инвалидирует коды).

Ответ: `[code str16]` — односторонний инвайт-код (URL
`shopot://i/...`, передаётся любым мессенджером; v1-коды `shopot1.`
тоже принимаются).
Ошибки: `TOO_MANY_INVITES`, `BAD_ARGS`.

#### `ACCEPT_INVITE` (5)
Payload: `[code str16][my_name str16]`. **Единственное** действие держателя
кода.
- `my_name` (≤ 32, пустой → `друг`) — увидит приглашающий.
- Код с адресом — подключение немедленное; без — ядро ждёт LAN-анонс
  приглашающего / автодозванивается.
- Статус подключения — по событиям `PRESENCE` (установка асинхронна).

Ответ: `[cid u32]`. Ошибки: `BAD_INVITE_CODE`, `BAD_ARGS`.

#### `LIST_CONTACTS` (6)
Payload: ∅. Ответ:
```
[count u32]
× { [cid u32][flags u8 (бит0 online, бит1 blocked)][last_seen_ms i64 (0 = неизвестно)][name str16] }
```

### 4.3 Сообщения

#### Entities форматирования (v2)

Каждый payload сообщений этого раздела (запрос, ответ, событие) несёт после
тела **хвост entities** — та же каноническая кодировка, что у конверта TEXT
на проводе (PROTOCOL.md §7.1):

```
[ent_count u8 ≤ 32]
× { [kind u8][offset u16][len u16][value_len u8][value байты] }
```

| kind | Смысл | value |
|---|---|---|
| 1 | жирный | — |
| 2 | курсив | — |
| 3 | подчёркнутый | — |
| 4 | зачёркнутый | — |
| 5 | спойлер | — |
| 6 | код (инлайн) | — |
| 7 | блок кода | тег языка, опционален |
| 8 | ссылка | URL, обязателен, ≤ 255 байтов |

- `offset`/`len` — БАЙТЫ UTF-8 в теле. Ядро не валидирует UTF-8; резать по
  границам символов при рендере — задача клиента.
- Правила, проверяемые ядром: `len ≥ 1`, `offset + len ≤ body_len`,
  записи отсортированы по offset, значение value по kind; пересечения
  разрешены (жирный + курсив на одном куске). Нарушение → `BAD_ARGS`
  (семантика) или `BAD_FRAME` (обрезанная структура).
- Байт счётчика есть всегда; форматирования нет → один байт `0x00`.

#### `SEND_MESSAGE` (7)
Payload: `[cid u32][body str16 ≤ 4096][хвост entities]`.
Ответ: `[msg_id 16][flags u8 (бит0 = queued)]`.
- Отправка офлайн-контакту НЕ ошибка: `queued=1` — уйдёт при появлении
  контакта (outbox; подтверждение — событие `MESSAGE_DELIVERED`).
- Ошибки: `NO_CONTACT`, `CONTACT_BLOCKED`, `BAD_ARGS` (пустое тело,
  кривые entities).

#### `SET_REACTION` (8) / `REMOVE_REACTION` (9)
Payload: `[cid u32][msg_id 16][codepoint u32]`.
- codepoint — Unicode code point, U+0000..U+10FFFF; вне диапазона →
  `UNSUPPORTED_REACTION`. Реакция требует живой сессии.
- Ответ: ∅. Ошибки: `NO_CONTACT`, `NO_SESSION`, `UNSUPPORTED_REACTION`,
  `CONTACT_BLOCKED`.
- Локальная история реакций фиксирует только постановки (снятие уходит
  пиру, но не пишется в лог — v1).

#### `GET_HISTORY` (10)
Payload: `[cid u32][limit u32]` (0 → 50; максимум 200 → `TOO_BIG`).
Ответ:
```
[total u32]   — всего записей у контакта
[count u32]
× { [flags u8 (бит0 mine, бит1 delivered)][msg_id 16][ts_ms u64][body str16][хвост entities] }
```
Записи старые → новые. `ts_ms` — локальное время записи (мс, epoch).
Хранится в шифрованном логе, переживает рестарты. Лога нет — пустой список
(`total=0, count=0`). Окно режется и `limit`, и бюджетом payload 1 МиБ:
при entity-тяжёлой истории `count` может быть меньше `limit`.

#### `GET_MESSAGE` (11)
Payload: `[msg_id 16]`. Ответ:
```
[cid u32][flags u8 (бит0 mine, бит1 delivered)][ts_ms u64][body str16][хвост entities]
[react_count u32]
× { [flags u8 (бит0 mine)][codepoint u32][ts_ms u64] }
```
Нет записи — `NOT_FOUND`. `бит1 delivered` ставится ACK-ом получателя
(`MESSAGE_DELIVERED`), а не фактом записи в сокет: отправленное сообщение
показывает `delivered=0` до прихода ACK. История отдаётся из кэша в памяти;
лог читается один раз на старте демона.

#### `SEARCH_MESSAGE` (23) / `GLOBAL_SEARCH_MESSAGE` (24)
Payload: `[cid u32][query str16][limit u32][offset u32]` (global: без `cid`).
Ответ: `[total u32][count u32] × {[cid u32] (только global)
[flags u8 (бит0 mine, бит1 delivered, бит2 fuzzy)][msg_id 16][ts_ms u64]
[body str16][хвост entities]}`. Регистронезависимые точные вхождения
сначала (новые → старые), затем нечёткие (пословный Левенштейн) для
запроса из одного слова. Ошибки: `BAD_ARGS` (пустой запрос), `TOO_BIG`.

### 4.4 Свой профиль

#### `SET_NAME` (12)
Payload: `[name str16 1..32]`. Ответ: ∅. Уходит пирам в PROFILE (онлайн —
немедленно; офлайн — при следующей сессии).

#### `SET_AVATAR` (13)
Payload: `[data str32 1..16000]` — байты картинки inline (формат ядром не
разбирается). Ответ: `[avatar_id 16][size u32]`.
- `avatar_id = SHA-256(data)[0..16]` — контент-адресация.
- Хранение: шифрованный лог, переживает рестарт.

#### `GET_AVATAR_ID` (14)
Payload: `[cid u32]`. Ответ: `[avatar_id 16]` (все нули — аватара нет).
Сами байты приходят событием `AVATAR_RECEIVED`: ядро само запрашивает их
(AVATAR_REQ) при расхождении id и самоисцеляется при реконнекте — клиенту
нужно только слушать событие и кэшировать по id.

### 4.5 Файлы

#### `SEND_FILE` (15)
Payload: `[cid u32][path str16]` — путь в ФС пользователя демона (клиент
кладёт файл, например, в `$HOME/.shopot/tmp/`, и передаёт путь).
- Лимит 64 МБ. Без живой сессии передача ставится в очередь (семантика
  outbox) и уходит при появлении сессии.
- Имя берётся из пути (basename, ≤ 64 байт).

Ответ: `[file_id 16][size u32][chunks u32]`.
- `file_id = SHA-256(файла)[0..16]`; приём сверяет хэш и сохраняет в
  `~/.shopot/files/<hex>` (0600). Дубликат не перекачивается.
- У получателя — событие `FILE_RECEIVED`; у отправителя — `FILE_SENT`,
  когда все чанки подтверждены.
- Ошибки: `NO_CONTACT`, `FILE_NOT_FOUND`, `TOO_BIG`, `BAD_ARGS`.

### 4.6 Звонки

| Метод | id | Payload | Ответ |
|---|---|---|---|
| `START_CALL` | 16 | `[cid u32]` | `[call_id 16]` |
| `ANSWER_CALL` | 17 | ∅ | ∅ |
| `END_CALL` | 18 | ∅ | ∅ |

- Голос: 16 кГц моно, E2EE, IMA-ADPCM 4:1, DTX (см. PROTOCOL.md §10).
- Одна линия на демон: `START_CALL` при активном звонке → `BUSY`;
  `ANSWER/END` без звонка → `NO_CALL`. `START_CALL` без сессии →
  `NO_SESSION`.
- Аудио идёт через fifo `~/.shopot/pcm/mic` и `~/.shopot/pcm/spk` (ядро
  читает/пишет).
- Состояния — события `CALL_STATE`.

### 4.7 Блокировка и транспорт

| Метод | id | Payload | Ответ |
|---|---|---|---|
| `BLOCK_CONTACT` | 19 | `[cid u32]` | ∅ |
| `UNBLOCK_CONTACT` | 20 | `[cid u32]` | ∅ |
| `CONNECT` | 21 | `[cid u32][addr str16]` | ∅ |
| `LISTEN` | 22 | `[addr str16][cid u32]` | ∅ |

`BLOCK_CONTACT`: трафик дропается, пир предупреждается. `CONNECT`/`LISTEN`
обычно не нужны (автодозвон/LAN справляются); ошибки — `NO_CONTACT`,
`TRANSPORT_FAILED`, `NO_RELAY`.

### 4.8 Чаты: закрепление, удаление, визитки

| Метод | id | Payload | Ответ |
|---|---|---|---|
| `PIN_CHAT` | 25 | `[cid u32]` | ∅ |
| `GET_PINNED_CHAT` | 26 | ∅ | `[cid u32]` (0 = нет) |
| `UNPIN_CHAT` | 27 | ∅ | ∅ |
| `DELETE_CHAT` | 28 | `[cid u32]` | ∅ |
| `SEND_CONTACT` | 29 | `[to_cid u32][contact_cid u32]` | ∅ |
| `PIN_MESSAGE` | 30 | `[cid u32][msg_id 16]` | ∅ |
| `UNPIN_MESSAGE` | 31 | `[cid u32][msg_id 16]` | ∅ |
| `GET_PINNED_MESSAGES` | 32 | `[cid u32]` | `[count u32] × {[msg_id 16]}` |

- Закреплённый чат один на демон (повторное закрепление идемпотентно).
  Закрепления переживают рестарты (шифрованный лог).
- `DELETE_CHAT` стирает переписку вместе с контактом: сессия гасится,
  outbox/файлы/история/реакции/закрепления чата вычищаются. Повторное
  знакомство с тем же человеком (новый инвайт от него) создаёт **новый cid
  с чистой историей**. До рестарта слот зарезервирован (cid остальных
  чатов не сдвигаются); после рестарта удалённые слоты не создаются —
  `LIST_CONTACTS` может вернуть перенумерованные cid, так что клиент в
  любом случае пересинхронизируется на бутстрапе.
- `SEND_CONTACT` пересылает визитку (имя, bundle и — если известен — адрес)
  по живой сессии; `contact_cid = 0` отправляет собственную визитку.
  Получателю приходит событие `CONTACT_CARD`. Карточка знакомит, но не
  подключает: добавить этого человека можно только его собственным
  инвайтом. Ошибки: `NO_CONTACT`, `CONTACT_BLOCKED`, `NO_SESSION`.
- `PIN_MESSAGE` требует, чтобы сообщение было в истории этого чата
  (`NOT_FOUND`); ≤ 16 закреплённых сообщений на чат (`TOO_BIG`). Порядок
  `GET_PINNED_MESSAGES` — порядок закрепления. `UNPIN_MESSAGE`
  идемпотентен.

## 5. События (EVENT)

Рассылаются всем подключённым клиентам, в любом порядке, `request_id = 0`.

| Имя | id | Payload |
|---|---|---|
| `MESSAGE_RECEIVED` | 1 | `[cid u32][msg_id 16][ts_ms u64][name str16][body str16][хвост entities]` |
| `MESSAGE_DELIVERED` | 2 | `[cid u32][msg_id 16]` |
| `PRESENCE` | 3 | `[cid u32][online u8 (1/0)][last_seen_ms i64]` |
| `REACTION` | 4 | `[cid u32][msg_id 16][op u8 (1 = add, 2 = remove)][codepoint u32][ts_ms u64]` |
| `CALL_STATE` | 5 | `[cid u32][call_id 16][state u8 (1 offer, 2 accept, 3 reject, 4 end)]` |
| `AVATAR_RECEIVED` | 6 | `[cid u32][avatar_id 16][data str16 ≤ 16000]` |
| `FILE_RECEIVED` | 7 | `[cid u32][file_id 16][size u32][name str16]` |
| `CONTACT_JOINED` | 8 | `[cid u32][name str16]` |
| `CONTACT_PROFILE` | 9 | `[cid u32][name str16][avatar_id 16]` |
| `BLOCKED_BY_PEER` | 10 | `[cid u32]` |
| `FILE_SENT` | 11 | `[cid u32][file_id 16][size u32][name str16]` |
| `CONTACT_CARD` | 12 | `[cid u32][name str16][bundle 64][addr str16]` |

- `MESSAGE_RECEIVED.ts_ms` = локальное время приёма, совпадает с ts в
  GET_HISTORY. msg_id — то, на что адресуются реакции.
- `PRESENCE`: рендерите статус только по этому событию — не опрашивать.
- `CALL_STATE`: reject/end всегда завершают аудиоконтур (после reject
  приходит и end).
- `CONTACT_JOINED` — держатель вашего инвайта подключился: контакт появился.
- `CONTACT_PROFILE` — имя/avatar_id контакта обновились (эхо PROFILE).
- `CONTACT_CARD` — пир переслал визитку третьего лица (SEND_CONTACT). cid —
  отправитель; `addr` пуст, если неизвестен. Карточка знакомит, но не
  подключает — добавить человека можно только его собственным инвайтом.

## 6. Лимиты (каноническая таблица)

| Лимит | Значение |
|---|---|
| payload кадра | 1 МиБ |
| тело сообщения | 4096 байт |
| отображаемое имя | 32 байта |
| аватар | 16000 байт (один провод-кадр); приём ≤ 1 в 5 мин |
| размер файла | 64 МБ |
| чанк файла | 16000 байт |
| одновременных передач на пира | 8 |
| параметр limit истории | 200 (0 → дефолт 50) |
| параметр limit поиска | 200 (0 → дефолт 50) |
| поисковый запрос | 4096 байт (регистронезависимо: свёртка ASCII + кириллица, прочие скрипты как есть) |
| outbox | 1000 записей, TTL 30 дней |
| живых приглашений | 4 (память демона, не переживает рестарт) |
| окно дедупа сообщений | 64 msg_id на контакт |
| закреплённых чатов | 1 на демон |
| закреплённых сообщений | 16 на чат |
| имя / адрес визитки | 32 / 64 байта |
| presence | PING после 4 с тишины; интервал 5 с; 3 пропуска → offline |
| диапазон прямых TCP-портов | 7777–7786 (первый свободный; все заняты → LAN-поиск выключен) |
| LAN-обнаружение | UDP-мультикаст 239.77.77.77:57770, анонсы 74 байта |
| демонов на `$HOME` | 1 (один путь UDS) |

## 7. Модель доставки

1. `SEND_MESSAGE` офлайн-пиру → ответ `queued=1`. GUI показывает
   «отправится позже».
2. Пир появился (LAN/автодозвон) → ядро само выгружает очередь.
3. Получатель каждого TEXT высылает ACK-конверт → отправителю приходит
   `MESSAGE_DELIVERED`: GUI показывает галочку «доставлено». Именно этот
   ACK — и только он — ставит бит `delivered` в записях `GET_HISTORY`/
   `GET_MESSAGE`/поиска (в том числе после рестарта); запись в офлайн-
   очередь доставкой не считается.
4. Дубликатов не бывает: msg_id дедупится на приёме.
5. Очередь переживает рестарт демона (шифрованный лог); лимиты: 1000
   записей, TTL 30 дней.

Presence: онлайн = живое соединение; тишина > 4 с → PING/PONG; 3 пропуска
→ offline (`PRESENCE` с online=0).

## 8. Жизненный цикл клиента

Бутстрап (аналог gateway READY):

```
подключиться к $HOME/.shopot/api.sock
GET_VERSION                       — проба готовности, сверка major
LIST_CONTACTS                     — полный снапшот контактов
для каждого cid: GET_HISTORY(cid,50) — начальная история
рендер; дальше состояние приходит только событиями
```

После бутстрапа клиент чисто событийный: presence, сообщения, реакции,
звонки, аватары, файлы — всё приходит событиями. Не опрашивать.

## 9. Сценарии (в терминах API)

### Добавление друга (один Wi-Fi)
```
A: CREATE_INVITE{name:"мама"}             → code
   (переслать код любым мессенджером)
B: ACCEPT_INVITE{code, my_name:"мама"}    → cid
   далее: сессия поднимается сама, PRESENCE online, текст ходит
A: слушает CONTACT_JOINED
```

### Дальние (за NAT, адрес известен)
A: `CREATE_INVITE{name, addr:"host:7777"}` → B: `ACCEPT_INVITE`.
Сокрытие IP: A поднимает `shopot relay host:port` где угодно и делает
`CREATE_INVITE` с relay=1.

### Офлайн-переписка
A пишет офлайн-B → `queued=1` → B запускает демон → ядро доставляет →
A: `MESSAGE_DELIVERED`.

## 10. Гарантии и границы

- Криптография: XX-подобное рукопожатие, AEAD-транспорт, двойной рэтчет —
  см. PROTOCOL.md. Клиент не касается ключей: сид живёт в
  `~/.shopot/zig-seed` (0600).
- Конкурентные клиенты: команды исполняются последовательно; события
  рассылаются всем.
- Права: `~/.shopot` — 0700, `api.sock` — 0700, `zig-seed` — 0600. Всё
  локально одному пользователю ОС.
- Джиттер-буфер звонка: кадры играются из очереди равномерно (~40–60 мс
  задержки); потери маскируются пропуском seq.
- Провод замаскирован под TLS 1.3 (fake-TLS). Пир видит ваш IP (P2P);
  скрытие — релей.
- Сокет и файлы принадлежат `$HOME`; несколько демонов на одном `$HOME`
  не поддержаны (один путь UDS).

## 11. Политика версионирования

- `GET_VERSION` возвращает `[major, minor, patch]`.
- **Major** — несовместимые изменения провода этого контракта; клиент обязан
  сверять major и отказываться работать с другой мажорной.
- **Minor** — совместимые добавления (новые методы, события, поля payload
  в конце структуры).
- Любое изменение контракта попадает в [CHANGELOG.md](../../CHANGELOG.md)
  до релиза.

## Приложение А. Справка по конвертам

Полные байтовые раскладки — PROTOCOL.md §7. Конверты строит только ядро,
не клиент. Полезно для чтения логов и событий:

TEXT (0x10) несёт msg_id/ts/тело + хвост entities форматирования; ACK (0x15) —
подтверждение доставки;
REACT (0x13) — op + codepoint; JOIN (0x40) — доказательство по инвайту;
PROFILE (0x42) — имя + avatar_id; CONTACT_CARD (0x43) — пересланная
визитка третьего лица; AVATAR/AVATAR_ACK/AVATAR_REQ
(0x50/0x51/0x52) — аватары; FILE_META/FILE_DATA/FILE_ACK (0x60/0x61/0x62) —
файлы; CALL_SIGNAL/CALL_AUDIO (0x30/0x31) — звонки; PING/PONG (0x20/0x21) —
presence; BLOCK_NOTICE (0x14) — блокировка.
