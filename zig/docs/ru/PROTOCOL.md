# Провод-протокол shopot v5

Нормативная байтовая спецификация протокола P2P-мессенджера shopot.
Реализация — `shopot-zig` (этот репозиторий). Английская версия:
[../PROTOCOL.md](../PROTOCOL.md).

**Правила провода**

- Никакого JSON и текстовых протоколов. Все целые — **little-endian**, если
  у поля явно не указано BE. Только фиксированные ширины полей, **varint
  запрещён**.
- Версия протокола вшита в транскрипт рукопожатия и заголовок хранилища.
  Несовместимое изменение = новый байт версии, никогда — тихое
  переопределение существующего поля.
- Нотация: `u8`/`u16`/`u32`/`u64` — беззнаковые целые 1/2/4/8 байт; `[N]` —
  N сырых байт; `str16` = `[len u16][байты]` (UTF-8, без терминатора).

## 1. Идентичность

| Объект | Построение |
|---|---|
| seed | 32 случайных байта, хранится только на устройстве владельца (`~/.shopot/zig-seed`, права 0600) |
| enc-пара | X25519, скаляр = HKDF-SHA256(seed, "shopot-id-v3")[0..32] |
| sign-пара | Ed25519, скаляр = HKDF-SHA256(seed, "shopot-id-v3")[32..64] |
| bundle | `enc_pk[32] || sign_pk[32]` — 64 байта, единственный материал личности, покидающий устройство |
| fingerprint | BLAKE2s-256(bundle), hex группами по 4 — сверка голосом против MITM |

Обе пары выводятся детерминированно: сид один восстанавливает личность.
Кто держит сид — держит личность; механизма отзыва нет.

## 2. Транспортное кадрирование (TCP)

Весь TCP-поток между пирами — последовательность кадров:

```
[len u16 LE][payload]
```

Два режима в одном потоке:

1. **handshake** — обмен из 3 сообщений XX-подобного рукопожатия (§3),
   обычными кадрами.
2. **session** — каждый кадр после:

```
[wirelen u16 LE][seq u64 LE][ChaCha20-Poly1305 box(pad(payload))]
```

- `obf_key = HKDF-SHA256(transcript_hash, "shopot-obf-v3")`.
- `nonce12 = 0x00000000 || seq` — счётчиковый, пара `(key, nonce)` не
  повторяется никогда по построению.
- AAD бокса — полный заголовок `[wirelen u16][seq u64]`: бокс привязан
  и к длине, и к счётчику.
- `seq` — счётчик кадров направления (tx у отправителя, rx у получателя,
  оба с нуля). Приём требует строго `seq == prev + 1`: повтор,
  перестановка и подмена кадра отбрасываются (`Tampered`).
- Полезная нагрузка выравнивается по **классу размеров**:
  128 / 256 / 512 / 1024 / 4096 / 16384 байт, нулевой паддинг плюс
  случайный довесок до 1/16 бакета, затем трейлер `[pad_len u16 LE]`.
  Максимум полезной нагрузки на кадр: 16356 байт.

**Что это даёт:** на проводе нет ни одного постоянного байта — ни магии,
ни строк версии, только равномерно случайные байты и квантованные длины.
Пассивный DPI-классификатор видит шум, статистически похожий на сжатый
бинарный поток. Это **маскировка** трафика, не анонимность: глобальный
наблюдатель всё равно видит факт соединения двух IP (§18, §15).

## 3. Рукопожатие (гибридное XX-подобное + ML-KEM-768, m1 → m2 → m3)

- `chaining_key = BLAKE2s-256("shopot-hs-v5-pq")`; хэш транскрипта =
  BLAKE2s-256 по всем сообщениям рукопожатия. Строка домена — это и есть
  версия провода: v5 = гибридный постквантовый KEX (эфемерный ML-KEM-768,
  FIPS 203, из `std.crypto`, смешан с классическим X25519-путём). Ядра
  разных версий выводят разные цепные ключи — их боксы m2/m3 не
  открываются, соединение падает сразу (fail-fast), а не даунгрейдится
  молча.
- **m1** (A → B, 1248 байт): `e_pub_A[32] || enc_pk_A[32] || mlkem_pk_A[1184]`
  — статический X25519-паблик инициатора идёт открытым текстом: респондент
  ищет контакт по нему до первого шифрования. `mlkem_pk_A` — **эфемерный**
  ключ инкапсуляции ML-KEM-768 инициатора (не входит в identity bundle).
- **m2** (B → A, 1232 байта): `e_pub_B[32] || mlkem_ct[1088] || бокс`.
  Ответчик инкапсулирует в `mlkem_pk_A` (`mlkem_ct`, 1088 байт); общий
  секрет KEM подмешивается в цепной ключ сразу после `DH(e_A, e_B)`.
  В боксе — `enc_pk_B[32] || sig_B[64]`; далее `DH(e_A, static_B)`.
  `sig_B = Ed25519(транскрипт)` покрывает транскрипт на момент m2 — т.е.
  весь m1, включая ML-KEM-паблик инициатора.
- **m3** (A → B, 112 байт): инициатор деинкапсулирует `mlkem_ct` (его KEM
  секрет выведен из того же эфемерного сида, что и X25519-пара, через
  отдельный HKDF-домен), `DH(static_A, e_B)`,
  `sig_A = Ed25519(транскрипт)` — транскрипт покрывает весь m2, включая
  KEM-шифротекст.
- Аутентификация KEM-шифротекста: подменённый ct деинкапсулируется в другой
  секрет (неявный отказ ML-KEM), цепные ключи расходятся и бокс m3 не
  открывается — вывод KEM аутентифицирован самим расписанием ключей плюс
  подписями транскрипта выше.
- Порядок выведения ключей (одинаков у сторон): `ee`
  (X25519 эфемерный-эфемерный) → общий секрет ML-KEM → `es` → `se`;
  финальная пара `(send_key, recv_key)` — из
  `HKDF-Expand(ck, "shopot-hs-finish-v5")`. Эфемерные сиды ML-KEM выводятся
  из сида рукопожатия через HKDF/BLAKE2s-домены `shopot-hs-mlkem-seed-v1` /
  `shopot-hs-mlkem-encap-v1` — продакшен-сид обязан быть из CSPRNG.
- **Гибридное свойство:** классическая безопасность держится при взломе
  ML-KEM; постквантовая конфиденциальность (устойчивость записанного сегодня
  трафика к decrypt-later) — при взломе X25519. Аутентификация остаётся
  Ed25519 (классической): *квантовый* активный MITM в рукопожатии не
  покрывается — PQ-подписи требуют отдельного изменения identity bundle
  (задокументированное ограничение, не молчаливое допущение). Ротация эпох
  рэтчета (§5) также остаётся X25519; PQ-гибриден только корень рукопожатия.
- Обе стороны сверяют подпись пира с **известным bundle контакта**. MITM
  с чужими ключами валится на m2/m3 (`BadSignature`), соединение
  закрывается.
- Дополнительно: статический X25519 из бокса m2/m3 сверяется с `enc_pk`
  известного bundle; несовпадение закрывает соединение (`KeyMismatch`).
  Практика noise-libp2p — проверка remote static после XX: подпись
  ответчика покрывает транскрипт *до* бокса, без сверки сессионные ключи
  могли выводиться с чужой статикой.
- Итог: `send_key`/`recv_key` (транспортный AEAD, §2), `transcript_hash`
  и через HKDF — начальные цепочки рэтчета (§5).

## 4. Шифрование сессии (sealed-кадры)

TEXT-конверты запечатываются **вторым** слоем поверх транспортного AEAD:

```
[0xA1][epoch u16 LE][counter u64 LE][comp u8][ChaCha20-Poly1305 box]
```

AD = весь 12-байтовый заголовок (флаг сжатия аутентифицирован — перевернуть
его, не сломав бокс, нельзя). Магия 0xA1 и байт эпохи делают sealed-кадр
самоописываемым внутри обфусцированного потока.

Сжатие payload (ROADMAP P1, zlib): если кодированный конверт ≥ 512 байт,
отправитель до запечатывания пробует `std.compress.flate` (zlib-контейнер,
уровень 6); `comp = 1` — в боксе zlib-поток, приёмник разжимает после
AEAD-open. Не сжимается: payload ниже порога (оверхед ~8 байт zlib не
отбить), уже-сжатое (магии PNG/JPEG/GZIP/ZIP/ZSTD) и всё, что не выигрывает
≥ 64 байт. Декомпрессия ограничена лимитом кадра — поток, разжимающийся
больше `max_encoded_len`, отбрасывается (guard от zip-бомб).

## 5. Рэтчет сообщений (симметричные цепочки + DH-эпохи)

Ключи на сообщение (симметричный рэтчет):

```
msg_key_i = HKDF-Expand(chain, "shopot-msg-v3" || counter_u64_LE)
chain     = HMAC-SHA256(chain, 0x02)          // сдвиг после использования
```

Приём по Double Ratchet spec (signal.org, §3.5):

- `peekRecv` выводит ключ под **ожидаемый** счётчик без сдвига цепочки;
  `commitRecv` сдвигает цепочку только после успешной расшифровки. Один
  битый кадр больше не рассинхронизирует стороны.
- Счётчик из кадра обязан совпасть с ожидаемым; повтор и перестановка
  отбрасываются.

DH-шаг (post-compromise security, «эпохи»):

- Каждые `rotate_every = 256` отправленных сообщений сторона генерирует
  **свежую** X25519-пару и шлёт паблик конвертом `RATCHET_KEY` (0x44):
  `[epoch u16 LE][dh_pub[32]]`. Конверт съедается слоем сессии, до движка
  не доходит.
- Получив свежий паблик пира, сторона при необходимости генерирует свою
  пару, отвечает зеркально и выполняет
  `dhStep(peer_fresh_pub, own_fresh_secret)`. Обе стороны выводят одинаковый
  общий секрет `DH(a_fresh, b_fresh)`, пересоздают обе цепочки
  (`root = HKDF(shared, "shopot-ratchet-v3")`), эпоха +1, счётчики в 0.
- Компрометация цепочек эпохи N не читает эпоху N+1; прошлые `msg_key`
  невыводимы.
- **Кадры «в полёте»:** пир мог отправить кадры старой эпохи после отсылки
  своего `RATCHET_KEY`, но до своего dhStep. Приёмник хранит снапшот
  приёмной цепочки предыдущей эпохи (`prev_recv`: эпоха, цепочка,
  счётчик) и расшифровывает опоздавшие им; их счётчики обязаны строго
  продолжать старую последовательность. Первый успешно расшифрованный кадр
  новой эпохи гасит снапшот — порядок потока гарантирует, что старых кадров
  больше не будет. Кадры неизвестной/просроченной эпохи отбрасываются.
- Вырожденный (низкопорядковый) `dh_pub` — нарушение протокола, сессия
  закрывается.
- Формат sealed-кадра и `RATCHET_KEY` **не** совместимы с ядрами до эпох
  (заголовок вырос 9 → 11 байт): обе стороны обязаны работать на одной
  версии ядра.

Транспортный AEAD остаётся сверху. Компрометация транспортного ключа не
раскрывает историю сообщений, и наоборот.

Движок шлёт TEXT только через `sendSealedText`; при реконнекте outbox
выгружается пачками: `[len][sealed] || [len][sealed] …` одним `writeAll`,
обф-слой кладёт пачку в один паддированный кадр (коалесценция).

## 6. Приглашения (v2, односторонние, JOIN)

Код приглашения (создаёт приглашающий, передаёт вне канала):

```
shopot://i/<base64url(bundle[64] || secret[16] || name_len u8 || name ≤32)>
[@host:port]            — необязательный прямой адрес
@r/<host:port>          — помечает адрес как релей (§15)
```

- 16-байтный `secret` одноразовый, живёт только в памяти приглашающего.
- Держатель кода выполняет ровно **одно** действие (accept) и всегда
  инициатор соединения: диалит адрес из кода или захватывает LAN-анонс
  приглашающего.
- Респондер с непогашенным приглашением принимает m1 от неизвестного
  `enc_pk` как *pending-сессию*: подпись m3 не проверяется (контакт
  неизвестен), окно 3 секунды.
- Первый конверт на pending-сессии обязан быть `JOIN` (0x40):

```
[bundle 64][name_len u8][name][sig 64][hmac 32]
```

  - `sig = Ed25519(sign_pk из bundle) над транскриптом` — привязывает
    заявленный bundle к ключам *этой* сессии (MITM не может предъявить
    чужой bundle).
  - `hmac = HMAC-SHA256(invite_secret, транскрипт)` — доказательство
    держателя кода; релей без секрета его не соберёт.
- Валидный JOIN: секрет гасится, контакт добавляется автоматически, сессия
  биндится на cid. Невалидный JOIN или таймаут — соединение закрывается.
- На pending-сессии **любой** конверт, кроме JOIN, закрывает соединение;
  порядок гарантирует ядро (JOIN до PROFILE).
- v1-коды (`shopot1.<base64url(bundle|name)>[@host:port]`) принимаются для
  совместимости: взаимный add обеими сторонами.

### 7.1. Форматирование сообщений (entities)

TEXT несёт опциональные entity-объекты (стиль Telegram MessageEntity):
диапазоны поверх тела + тип форматирования + опциональное значение.

```
хвост TEXT: [ent_count u8 ≤ 32]
            × ent_count { [kind u8][offset u16][len u16][value_len u8][value] }
```

- Байт счётчика есть ВСЕГДА (0 entities → один байт `0x00`): кадр v3 без
  хвоста не декодируется (Truncated) и отбрасывается.
- `offset`/`len` — БАЙТЫ UTF-8 в body — не code points и не UTF-16-юниты.
  Ядро не валидирует UTF-8 (как и само body); резать по границам символов
  при рендере — задача клиента.
- `kind`: 1 bold, 2 italic, 3 underline, 4 strikethrough, 5 spoiler,
  6 code (инлайн), 7 pre (value = тег языка, опционален), 8 link
  (value = URL, обязателен). 9+ — резерв; новый kind = новая версия
  протокола. Неизвестный kind на приёме — кадр отбрасывается.
- `value` ≤ 255 байтов; пустой у всех kind, кроме `link`/`pre`.
- Правила (на кодировании и на декодировании): `len ≥ 1`,
  `offset + len ≤ body_len`, записи отсортированы по `offset`;
  **пересечения диапазонов разрешены** (bold + italic на одном куске).
- Бюджет: ≤ 32 entities, суммарно ≤ ~12.5 КБ хвоста — максимальный TEXT
  остаётся одним obf-кадром класса 16384, форма трафика не меняется.

Те же канонические байты хвоста дословно переиспользуются в записях лога
`msg`/`outbox` (§13) и в payload UDS-апи (SEND_MESSAGE, GET_HISTORY,
GET_MESSAGE, MESSAGE_RECEIVED) — одна кодировка на всех слоях.

### 7.2. Записи синхронизации устройств (SYNC 0x45)

*Линк устройства* — контакт, чей bundle равен собственному у отправителя
(две установки с одним сидом личности). По этой сессии ядро реплицирует
записи шифрованного лога партиями; семантика очереди — как у outbox
(ограниченная очередь на устройство, одна партия в полёте, SYNC_ACK
освобождает, обрыв сессии возвращает партию в голову очереди, повторная
доставка идемпотентна на приёме).

```
recs:  count × { [kind u8][mac[32]][len u16 ≤ 4096][data] }
mac    = HMAC-SHA256(HKDF(seed, "shopot-device-sync-v1"), kind ‖ data)
```

- `data` — payload записи лога с переводом локальных полей `cid` в bundle
  пира (64 Б): записи msg/react/file получают префикс `bundle[64]` вместо
  `cid u16`; запись ack сжимается до глобального `msg_id[16]`; записи
  contact/block/cfg/client проходят как есть.
- Виды записей (пространство синхронизации, НЕ kind-ы лога): msg 1,
  contact 2, block 3, react 4, ack 5, file 6, client 7, cfg 8.
- Ключ MAC выводится из сида личности: подделать принятую запись может
  только устройство с тем же сидом; прочее отбрасывается молча.
- Применение идемпотентно (дедуп msg_id, существование контакта, MAC-множество
  клиентских записей, cfg — последняя побеждает) и НИКОГДА не ставит
  результат обратно в очередь (нет петли эха).
- Лимиты: одна запись ≤ 4034 байтов, ≤ 64 записей / 16000 байтов в партии,
  512 записей / 2 МиБ на очередь устройства. Аватары и закрепления в v1
  не реплицируются.

## 8. Доставка офлайн-сообщений (outbox)

- Нет сессии — TEXT не ошибка: он уходит в outbox (память + запечатанная
  запись `OUTBOX` в шифрованном логе; на диске ноль открытого текста).
- Сессия поднялась (анонс, автодозвон, ручной connect) — ядро шлёт все
  не-ACKed записи **пачками по 64** конверта (коалесценция, §5). Повтор
  после реконнекта идемпотентен благодаря дедупу.
- Дедуп: приёмник держит окно 64 последних `msg_id` на контакт; повторный
  TEXT отбрасывается, ACK зеркалится заново.
- ACK (0x15) высылается получателем **каждого** TEXT: `msg_id` гасит запись
  outbox отправителя; приложение получает событие «доставлено».
- Капа outbox: 1000 записей, старое вытесняется; TTL 30 дней.
- Автодозвон офлайн-контактов по последнему известному адресу (из кода или
  LAN-анонса): backoff 1 с → 60 с с джиттером. Первый LAN-анонс уходит
  сразу при старте демона — пир с очередью узнаёт о возврате за ~RTT.
- `ts_ms` внутри TEXT — локальное время записи отправителя и остаётся
  приватным (не wall clock); принимающая сторона пишет в историю своё
  локальное время приёма.

## 9. Передача файлов (докачка)

- `FILE_META` (0x60) анонсирует файл: контент-адресованный
  `file_id = SHA-256(данных)[0..16]`, имя ≤ 64 байт, размер ≤ 64 МБ,
  полный SHA-256. Приёмник отвечает на **каждый** FILE_META позиционным
  `FILE_ACK` (0x62): `got` = сколько чанков уже есть — 0 для свежего
  приёма, `total` для файла уже в кэше (короткое замыкание).
- `FILE_DATA` (0x61): `seq` с нуля, ≤ 16000 байт на чанк (один obf-кадр
  класса 16384). Приёмник складывает строго по порядку; дыра не
  запрашивается повторно (окно отправителя само доедет).
- FILE_ACK каждые 8 чанков плюс финальный: `got` — точка докачки.
  Отправитель держит окно 64 неподтверждённых чанков (~1 МБ) и состояние
  передачи до полного подтверждения — outbox для файлов. Передачи без
  живой сессии ставятся в очередь и уходят при появлении сессии.
- Разрыв и реконнект: отправитель заново анонсирует FILE_META со своей
  позицией `last_ack`; позиционный ответ приёмника выставляет точку
  докачки (0 — заново, `total` — уже всё). Ответ `got < last_ack` в
  обычном режиме = приёмник сбросил приём (битый SHA) — передача заново
  с нуля.
- Все чанки подтверждены → ядро гасит запись передачи и поднимает событие
  UDS `FILE_SENT`; приём завершённого файла — `FILE_RECEIVED` (проверка
  SHA обязательна; несовпадение — сброс приёма, отправителю FILE_ACK 0).
- Идемпотентность: повторная отправка того же `file_id` не дублирует
  передачу (контент-адресация); приём уже собранного файла — короткое
  замыкание позиционным FILE_ACK. Капа: 8 одновременных передач на пира.
- Принятые файлы хранятся в `~/.shopot/files/<id_hex>` (права 0600).

## 10. Звонки (голос)

- Аудио: PCM s16le моно 16 кГц, кадры 20 мс → 640 байт. IMA-ADPCM 4:1 →
  блоки 164 байта (72 кбит/с). Payload CALL_AUDIO: `[codec u8][блок]`,
  codec 1 = PCM (640), 2 = ADPCM (164). Тишина (DTX): 1 из 25 кадров —
  keepalive.
- Каждый аудиокадр шифруется дважды:
  1. транспортный AEAD (§2);
  2. одноразовый ключ кадра: `key_i = HKDF-Expand(call_secret,
     "shopot-call-v3" || seq_u32_LE)`, где
     `call_secret = HKDF(transcript_hash || call_id[16], "shopot-call-v3")`.
  - Ключ на `seq` используется ровно один раз; журнал seq не хранится —
    повтор seq отбрасывается приёмником (отдельная машина состояний,
    окно 64).
  - Итог: компрометация любого уровня не даёт прошлых кадров звонка
    (forward secrecy на кадр).
- Джиттер-буфер: приёмник кладёт кадры в очередь 16 слотов, плейаут тиком
  20 мс — минимум 3 кадра или 60 мс выдержки до старта; 8+ в очереди —
  слив; дыра 200 мс — пропуск seq (маскирование потери). Вносимая
  задержка: ~40–60 мс.
- Аудио-ввод/вывод — через fifo `~/.shopot/pcm/mic` и `~/.shopot/pcm/spk`
  (ядро читает/пишет сырой PCM); громкость и AGC — на клиенте, ядро их не
  трогает.

## 11. Presence

- Онлайн = живое соединение + метки входящих кадров. Любой входящий кадр
  обновляет `last_seen_ms` пассивно (ноль отдельных запросов).
- Только после 4 с тишины шлётся PING: 13 байт полезной нагрузки
  (тег + seq u32 + ts u64), 15 байт на проводе с заголовком кадра; PONG —
  зеркально.
- 3 пропущенных 5-секундных интервала → offline. Пропавший пир опрашивается
  всё реже: 5 с → 10 → 20 → 40 → 60 с (капа). Никаких broadcast и
  интервалов-опросов.
- Точность: миллисекундные метки ts_ms в каждом PING/PONG и TEXT.

## 12. Блокировка

`BLOCK_NOTICE` (0x14) сообщает пиру, что он заблокирован. Локально записи
заблокированного контакта отбрасываются до разбора конвертов. Список живёт
в шифрованном логе (kind `BLOCK`).

## 13. Хранилище

Только-дописываемый шифрованный лог (вместо любой БД):

```
заголовок (12 Б): [version u8 = 3][reserved u8 ×3][epoch u32][base_seq u32]
запись:           [len u16][nonce12][ChaCha20-Poly1305 box]
nonce             = 0x00000000 || epoch_u32 || seq_u32   (детерминированный)
открытый текст:   [kind u8][seq u32][payload]
storage_key       = HKDF-SHA256(Expand(HKDF-Extract("shopot-store-v3", seed), "", 32))
```

- AAD каждого бокса — `epoch u32 LE` файла, в котором запись живёт:
  записи нельзя перенести между эпохами.
- Типы записей и раскладки payload:

| kind | значение | payload |
|---|---|---|
| msg | 1 | `[cid u16][flags u8 (бит0 mine, бит1 delivered, бит2 reply)][msg_id 16][ts u64]` — бит2 вставляет `reply_to[16]` перед `[len u16][body][хвост ents]` |
| contact | 2 | запись контакта (bundle, имя, адреса; опциональный хвостовой байт роли линка устройства, §7.2) |
| block | 3 | заблокированный контакт |
| react | 4 | запись реакции |
| set | 5 | `[ключ u8][значение]`: 1 = мой `avatar_id[16]`, 2 = моё имя |
| tombstone | 6 | `u32 LE` seq удаляемой записи |
| outbox | 7 | под u8: 1 = `[cid u16][flags u8 (бит2 reply → reply_to 16)][msg_id 16][ts u64][len u16][body][хвост ents]`, 0 = `[cid u16][msg_id 16]` (доставлено, гасится при рестарте) |
| avatar | 8 | `[avatar_id 16][len u16][data ≤ 16000]` |
| file | 9 | `[cid u16][file_id 16][size u32][len u8][name]` |
| cfg | 10 | blob конфигурации `[ver u8][flags u32][server_addr str16][tor_addr str16]` (побеждает последняя запись; §17) |
| client | 11 | `[tag u8 ≠ 0xFF][ts u64][len u16][data ≤ 65000]` — собственные записи клиента (UDS WRITE_DB), живая область ≤ 16 МиБ |

- Tombstone помечает запись мёртвой в индексе; компакция переписывает живые
  записи в новый файл с `epoch+1`, tombstone и мёртвые записи исчезают.
- Хвост ents (§7.1; ядра v4 пишут его всегда, с байтом счётчика) читается
  **толерантно**: запись, кончающаяся сразу после body — легаси v3,
  декодируется как «без форматирования» — история переживает апгрейд без
  миграции. Структурно битый хвост — запись пропускается.
- Любая структурная аномалия или провал аутентификации бокса при чтении —
  файлу ноль доверия (`Corrupt`).
- На диске нет ни байта открытого текста, имён или метаданных. Ключ
  хранилища живёт в памяти и обнуляется в `deinit`.

## 14. Профили и аватары

- `PROFILE` (0x42) — эхо при каждом установлении сессии: текущее имя +
  текущий `avatar_id`.
- `avatar_id = SHA-256(картинки)[0..16]` — контент-адресация: дедуп
  бесплатно, новая картинка = новый id. Байты аватара (≤ 16000, один obf-
  кадр класса 16384) ходят только внутри E2E-сессии, на диске запечатаны
  (лог kind `AVATAR`).
- Самоисцеление: приёмник видит в PROFILE id без локального кэша → шлёт
  `AVATAR_REQ` (0x52) → владелец перекачивает `AVATAR` (0x50), приём
  подтверждается `AVATAR_ACK` (0x51); приём сверяет SHA-256 с id.
- Лимит 16000 — осознанное отклонение от 32K: 32K не влезает в один кадр.
  Рейт-лимит на приём: один аватар в 5 минут (анти-спам).
- Картинка — недоверенный бинарник; декодирование — работа клиента, ядро
  байты не разбирает. Даунскейл до 128×128 — ответственность клиента
  отправителя; ядро только отвергает сверхлимит.

## 15. Релей (скрытие IP)

Само-хостнутый байтовый сплит (`shopot relay <host:port>` на любом
сервере): ноль состояния shopot, ноль своей крипты (E2EE сквозная; релей
видит TLS-подобный шум). Обе стороны — клиенты релея:

```
клиент → релей: [17 03 03 0020][marker 32]     (TLS-подобная запись)
релей → обоим:  [17 03 03 0001 5A]              (спарен)
далее:          прозрачный сплит байтов (fake-TLS поток сквозной)
```

- Два вида marker-а, оба `HMAC-SHA256` по общему секрету:
  - фаза инвайта: `HMAC(invite_secret, "shopot-relay-v1")` — вычисляют обе
    стороны инвайта; релей только сверяет значения (одноразовый, гасится
    вместе с инвайтом);
  - фаза присутствия: `HMAC(pair_secret, "shopot-relay-presence-v1")`, где
    `pair_secret = X25519(мой_статический_enc, enc-паблик_пира)` — pre-message
    `ss` из Noise KK: обе стороны выводят его из долговременных ключей без
    единого обмена; релей его вычислить не может.
- Семантика слота: первый коннект с marker-ом «владеет» слотом, второй
  спаривается; при активной паре лишние коннекты закрываются. По завершении
  пары слот **освобождается** — перерегистрироваться и спариться заново
  может любая сторона (это и даёт присутствие).
- Инвайт-код с релеем: `shopot://i/<b64>@r/<host:port>`.
- A-сторона (`invite <имя> relay <addr>`) держит регистрацию и
  переподключается при обрыве, пока инвайт не погашен; B-сторона
  (`add <код>`) диалит релей marker-ом, далее обычные handshake+JOIN
  поверх сплита.
- Постоянное присутствие после JOIN: контакт помнит relay-адрес (в
  шифрованном логе контактов — переживает рестарт демона), и presence-цикл
  перерегистрирует слот контакт-маркером, пока нет живой сессии. Появляется
  пир — релей спаривает коннекты, поднимается новая сессия — **новый инвайт
  не нужен**. Роль рукопожатия детерминирована: инициатор — сторона с
  лексикографически меньшим bundle. Блокировка контакта останавливает
  присутствие, разблокировка возвращает.
- Замечание: компромисация статик-статик X25519 раскрывает marker (релейный
  DoS/занятие слота — полное XX-рукопожатие всё равно аутентифицирует);
  скомпрометированный ключ identity и так game-over.
- Релей **не** скрывает адреса от самого релея; DPI видит TLS-подобный
  поток к релею и обратно.

## 16. Fake-TLS v2 (маскировка провода)

Весь TCP-поток (m1/m2/m3 + obf-кадры) завёрнут в побайтовую имитацию
Chrome ↔ TLS 1.3:

- **ClientHello** — байтовый шаблон реального захвата Chrome 155 (16 шифров,
  19 расширений: кейшеры X25519MLKEM768 + x25519, ECH-grease, trust anchors,
  ALPS, ALPN h2/http1.1); на каждое соединение рандомизируются random,
  session_id, GREASE-поинты, кейшеры, ECH-шум, SNI (из списка невинных
  доменов) и **порядок средних расширений** (Fisher-Yates, как BoringSSL).
  Затем CCS и «зашифрованный» Finished (запись 52) — направление
  client→server побайтово совпадает с настоящим Chrome.
- **Серверный флайт**: ServerHello (с echo session_id клиента, AES-128-GCM,
  кейшер x25519) + CCS + 4 «зашифрованные» записи (EE / Certificate /
  CertificateVerify / Finished) правдоподобных случайных размеров.
- **Данные**: записи `[17 03 03 len u16 BE][payload][16 байт псевдо-тега
  AEAD]`, len = payload + 16, максимум 16400 — в точности квантование AECD
  настоящего TLS 1.3. Тег — шум PRNG (контент выше уже шифруется AEAD
  сессии).
- **Закрытие**: close_notify (запись 18) перед TCP FIN; пир трактует её как
  `Closed`. 2-байтовый payload `[01 00]` зарезервирован.
- **Релейный фрейминг** (§15) согласован с квантованием: маркер-запись
  len 48 (32 + псевдо-тег), сигнал спаривания — запись len 18 (минимум AECD).
- Скорость: один syscall write на TLS-запись (стейджинг заголовка+payload+
  тега), косметический шум — per-connection PRNG, ноль аллокаций на кадр.

Это защищает только от пассивной DPI-классификации (JA3/JA4, разбор записей,
статистика размеров). Это **не** настоящий TLS: активный MITM с
терминированием увидит подделку (настоящих ключей нет), тайминг-анализ
(Finished без RTT-паузы) не имитируется. Скрытие IP и обход IP-whitelist —
работа релея (§15). Обрамление v2 несовместимо с faketls первого поколения:
обе стороны должны быть одного релиза ядра (то же правило, что для sealed
frames, §19).

## 17. API ядра (UDS)

`shopot serve` поднимает UDS-сокет `$HOME/.shopot/api.sock` (0700) с
бинарным кадровым протоколом — единственный интерфейс ядра; GUI-клиенты
работают через него. Раскладка кадров, методы, машинные коды статусов,
события и сценарии — **[../CORE-API.md](../CORE-API.md)** (версия API 2.4.0).

## 18. Что видит наблюдатель

Честные пределы дизайна:

| Наблюдатель | Узнаёт |
|---|---|
| DPI на пути | неотличимый от Chrome TLS 1.3-поток с AECD-квантованием размеров записей (§16); маркеров протокола нет |
| пассивный сетевой наблюдатель | сам факт общения двух IP, объём, тайминги |
| релей (само-хостнутый) | оба endpoint-IP, объём, тайминги; контент — нет |
| контакт | всё, что ему отправляют, подтверждения доставки, текущие имя/аватар |
| любой с доступом к устройству | сид → личность → расшифрованная история |
| глобальный адверсарий, коррелирующий трафик | endpoints каждого соединения (нет cover-трафика, нет микширования) |

Не покрывается: защита метаданных в масштабе сети, отказ в обслуживании,
компрометация ОС, multi-device (одна личность = один живой инстанс,
by design).

## 19. Версионирование и совместимость

- Провод-протокол версионируется **байтом версии**, вшитым в транскрипт
  рукопожатия (домен `shopot-hs-v5-pq`, т.е. 5) и заголовок хранилища (3).
- Несовместимые изменения требуют бампа байта версии и записи в
  [../../CHANGELOG.md](../../CHANGELOG.md). Тихое переопределение существующих полей
  запрещено.
- v5 (гибридное ML-KEM-768-рукопожатие, §3) несовместима на проводе с v4:
  домен рукопожатия поднят, m1/m2 выросли (KEM-паблик 1184 байт, шифротекст
  1088 байт), ядра смешанных версий не поднимают сессию вовсе (fail-fast;
  ядро v4 отвергает кадр m1 длиной 1248 байт сразу, ядро v5 никогда не
  откроет бокс v4). Заголовок хранилища остаётся 3: история переживает
  апгрейд.
- v4 (entities в TEXT, §7.1) была так же несовместима с v3 на проводе
  (домен рукопожатия поднят). Хвост `msg`/`outbox` в хранилище остался
  аддитивным и читается толерантно.
- Мажорное изменение контракта UDS-апи (CORE-API.md) поднимает мажорную
  версию, возвращаемую `GET_VERSION`.
- Sealed-кадры (0xA1 + заголовок с эпохой) и `RATCHET_KEY` несовместимы с
  ядрами до эпох: обе стороны обязаны работать на одной версии ядра.
