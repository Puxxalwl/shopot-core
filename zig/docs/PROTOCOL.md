# shopot wire protocol v3 (binary)

Никакого JSON. Всё little-endian, поля фиксированной ширины. Буферы фиксированные,
varint запрещён. Версия протокола заявляется в handshake transcript и в заголовке
хранилища; несовместимые изменения = новая версия байтом, а не договорённость.

## Идентичность
- seed 32 байта (владелец = личность, хранится только у владельца).
- enc = X25519 keypair, sign = Ed25519 keypair; оба скаляра = HKDF-SHA256(seed, "shopot-id-v3") (64 байта).
- bundle = enc_pk (32) || sign_pk (32) — 64 байта, то, что передаётся для добавления.
- fingerprint = BLAKE2s-256(bundle), hex группами по 4 — сверка голосом против MITM.

## Уровень транспорта (TCP)
Каждый кадр: [len u16 LE][payload]. Два режима:
1. **handshake** — 3 сообщения XX-подобного рукопожатия (см. ниже).
2. **session** — каждый кадр = [seq u64 LE][ChaCha20-Poly1305 box], nonce12 = 0000||seq,
   ключ obf = HKDF-SHA256(transcript_hash, "shopot-obf-v3"). seq — счётчик кадров
   направления (tx у отправителя, rx у получателя, оба с нуля): повтора пары
   (key, nonce) не бывает по построению, приём ждёт строго seq+1 — повтор,
   перестановка и подстановка кадра отбрасываются (Tampered). AAD бокса —
   полный заголовок [wirelen u16][seq u64].
   Полезная нагрузка выравнивается по классам размеров: 128/256/512/1024/4096/16384
   с нулевым паддингом и случайным довеском до 1/16 бакета. На проводе нет ни одного
   постоянного байта: ни магических чисел, ни строк версии — только равномерно
   случайные байты и квантованные длины. Это маскировка трафика (DPI видит шум,
   похожий по распределению размеров на сжатый бинарный поток), не анонимность:
   глобальный наблюдатель по-прежнему видит сам факт соединения двух IP.

## Рукопожатие (XX-подобное, m1 -> m2 -> m3)
- chaining key init = BLAKE2s-256("shopot-hs-v3"); хэш transcript = BLAKE2s-256.
- m1: e_pub_A || enc_pk_A (64 байта) — enc_pk инициатора идёт открытым текстом:
  респондент находит контакт до расшифровки.
- m2: e_pub_B, DH(ee), enc_pk_B, DH(es), sig_B(Ed25519 над transcript).
- m3: DH(se), sig_A(Ed25519 над transcript).
- Обе стороны проверяют сигнатуры против известного bundle контакта — MITM с
  чужими ключами отбрасывается на m2/m3 (ошибка BadSignature).
- Итог: send_key/recv_key (ChaCha20-Poly1305 транспорт), transcript_hash.
- obf_key = HKDF(transcript, "shopot-obf-v3").

## Сообщения (двойное шифрование)
TEXT-конверты дополнительно запечатаны симметричным рэтчетом:
msg_key_i = HKDF-Expand(chain, "shopot-msg-v3" || counter_u64_LE), chain = HMAC(chain, 0x02);
каждые 256 сообщений — DH-шаг (X25519 заново), root = HKDF(dh, "shopot-ratchet-v3").
Транспортное шифрование остаётся сверху. Компрометация транспортного ключа не
раскрывает историю сообщений, и наоборот.

## Односторонние приглашения (invite v2, JOIN)
- Код: `shopot://i/` + base64url(bundle[64] || secret[16] || name_len u8 || name ≤ 32)
  + необязательный `@host:port`. Секрет одноразовый, живёт в памяти приглашающего.
- Держатель кода выполняет ЕДИНСТВЕННОЕ действие (add) и всегда инициатор соединения:
  адрес из кода, либо LAN-анонс приглашающего (мультикаст-захват).
- Респондер с непогашенным приглашением поднимает m1 от неизвестного enc_pk как
  pending-сессию: sig в m3 НЕ проверяется (контакт неизвестен), окно 3 с.
- Первый конверт обязан быть JOIN: sig = Ed25519(sign_pk из bundle) над transcript —
  привязывает заявленный bundle к ключам ЭТОЙ сессии (MITM не может предъявить
  чужой bundle); hmac = HMAC-SHA256(invite_secret, transcript) — доказывает
  держателя кода (relay без кода HMAC не соберёт).
- Валидный JOIN: секрет гасится, контакт добавляется автоматически, сессия
  биндится на cid. Невалидный/таймаут — соединение закрывается.
- v1-коды (`shopot1.`) сохранены для совместимости: взаимный add обоими сторонами.

## Конверты (внутри кадра session-уровня)
| Тег  | Имя          | Поля (LE)                                        |
|------|--------------|--------------------------------------------------|
| 0x10 | TEXT         | msg_id[16], ts_ms u64, body[u16 ≤ 4096]           |
| 0x13 | REACT        | msg_id[16], op u8 (1 add / 2 remove), code u8     |
| 0x14 | BLOCK_NOTICE | reason u8                                         |
| 0x15 | ACK          | msg_id[16]                                        |
| 0x20 | PING         | seq u32, ts_ms u64                                |
| 0x21 | PONG         | seq u32, ts_peer_ms u64                           |
| 0x30 | CALL_SIGNAL  | op u8 (0 offer/1 accept/2 reject/3 end), call_id[16] |
| 0x31 | CALL_AUDIO   | seq u32, data[u16 ≤ 1024]                         |
| 0x40 | JOIN         | bundle[64], name[u8 ≤ 32], sig[64], hmac[32]      |

## Доставка офлайн-сообщений (outbox)
- Нет сессии — TEXT не теряется: ядро кладёт его в outbox (память + запись
  kind OUTBOX в шифрованном логе, на диске ноль открытого текста).
- Сессия поднялась (анонс, автодозвон, ручной connect) — ядро шлёт ВСЕ
  не-ACKed записи: повтор после реконнекта идемпотентен благодаря дедупу.
- Дедуп: приёмник держит окно 64 последних msg_id на контакт; повторный
  TEXT отбрасывается, ACK зеркалится заново.
- ACK (0x15) высылается получателем КАЖДОГО TEXT: msg_id гасит запись outbox
  отправителя, приложение получает событие «доставлено».
- Капа outbox 1000 записей (старые вытесняются), TTL 30 дней.
- Автодозвон офлайн-контактов по последнему известному адресу (из кода или
  LAN-анонса): backoff 1с → 60с с джиттером. Первый анонс — сразу при старте
  демона: пир с очередью узнаёт о возврате за ~RTT.

## Звонки
Аудио: PCM s16le mono 16 kHz, кадры 20 мс. Каждый кадр шифруется ДВАЖДЫ:
1. транспортный AEAD (см. session),
2. одноразовый ключ звонка: key_i = HKDF-Expand(call_secret, "shopot-call-v3" || seq_u32_LE),
   call_secret = HKDF(transcript_hash || call_id[16], "shopot-call-v3").
Ключ seq использован один раз; журнал seq не хранится — повтор seq отбрасывается
принимающим (отдельная машина состояний, окно 64). Итого: компрометация любого
уровня не даёт предыдущих кадров звонка (forward secrecy per frame).

## Presence
- Онлайн = живое соединение + метки входящих кадров. Любой входящий кадр
  обновляет last_seen_ms (пассивно, ноль отдельных запросов).
- Только при тишине > 4 с шлётся PING: 13 байт полезной нагрузки (tag u8 +
  seq u32 + ts u64), 15 байт на проводе с заголовком кадра; PONG — зеркально.
- 3 пропущенных интервала (5 с) = offline. Никаких broadcast/интервалов-опросов.
- Точность: миллисекундные метки ts_ms в каждом PING/PONG и в TEXT.

## Блокировка
BLOCK_NOTICE уведомляет, что отправитель заблокирован; локально записи
заблокированного контакта отбрасываются до разбора конвертов. Список живёт
в шифрованном логе (kind BLOCK).

## Хранилище
Только-дописываемый лог: [header: version u8, epoch u32, base_seq u32]
[records: [len u16][nonce12][ChaCha20-Poly1305(kind u8, seq u32, payload)]],
ключ = HKDF(seed, "shopot-store-v3"). Компакция переписывает живые записи с
epoch+1. На диске нет ни одного байта открытого текста, имён или метаданных.

## Профили и аватары
PROFILE (0x42) — эхо при каждом установлении сессии: имя + текущий avatar_id.
Расхождение известного id с PROFILE — пир шлёт AVATAR_REQ, владелец
перекачивает AVATAR (контент-адресован SHA-256(data)[0..16], ≤ 16000 байт —
один obf-кадр класса 16384). Приём сверяет хэш с id. Лимит 16000 —
осознанное отклонение от 32K: 32K не влезает в один кадр.

Важно: на pending-сессии (до JOIN) любой конверт, кроме JOIN, закрывает
соединение — держатель инвайта обязан подать JOIN ПЕРВЫМ (ядро гарантирует
порядок: JOIN до PROFILE).

## UDS-апи (интерфейс ядра)
`shopot serve` поднимает UDS-сокет `$HOME/.shopot/api.sock` (построчный
протокол, \n-конец, без JSON). Это ЕДИНСТВЕННЫЙ интерфейс ядра: клиенты
(натив, TUI, скрипты) подключаются к нему. Полная спецификация команд,
событий и сценариев — **CORE-API.md**.

- команды: `msg`, `gethistory`, `getmessage`, `react`, `call`, `answer`,
  `hangup`, `block/unblock`, `contacts`, `invite`, `add`, `help`, `quit`;
- ответы — строки-результаты; события ядра: `msg <cid> <имя> <текст>`,
  `sys <cid> <текст>`, `presence <cid> on|off`;
- события приходят всем подключённым клиентам.

## История сообщений
Каждое отправленное/полученное TEXT записывается в шифрованный лог
(kind MSG: [cid u16][flags u8: бит0 mine, бит1 delivered][msg_id 16]
[ts u64 локального времени][len u16][body]) — основа gethistory/getmessage.
Метка ts_ms в конверте TEXT остаётся приватной (не wall clock).
