# BACKEND_ANSWERS — ответы ядра shopot-core на вопросы GUI

> **⚠️ ПРОТОКОЛ ЗАМЕНЁН (API 1.0.0).** UDS-апи полностью переделано на
> бинарные кадры: построчный строковый протокол (`msg <cid> ...`,
> теги `@n`, ответы `! код: текст`, события `imsg/sys/presence/call`)
> **удалён**. Все примеры провод-формата ниже — исторические; семантика
> ответов (кто ставит ts, чей msg_id, дедуп, очередь) сохранилась.
> Единственный источник истины по формату — **CORE-API.md** (бинарная
> спецификация): методы GET_VERSION/SEND_MESSAGE/SET_REACTION/...,
> статусы-коды (BAD_ARGS, NO_CONTACT, UNSUPPORTED_REACTION, ...),
> события MESSAGE_RECEIVED/PRESENCE/CALL_STATE/....

Ответ на BACKEND_QUESTIONS.md (после S1/MockLink). По каждому Q: факт
кода, верно ли допущение GUI, что делать в UdsLink. Источник истины —
zig/docs/CORE-API.md; противоречия трактуются в пользу CORE-API.
Пометка **ФОРМАТ** = расхождение с допущением GUI, нужно менять код GUI.

## События (стрим LinkEvent)

### Q1. Эхо исходящих — **допущение верно**
Ядро НЕ эхоит исходящие в стрим: `imsg` фан-аутится только из приёмного
пути (onTextEv). Исходящее рисуется локально — как вы и делаете.
НО: **id исходящих генерирует ЯДРО, не клиент**. Ответ `msg <cid> <текст>`
возвращает строку `msg_id <hex32>` (128 бит, CSPRNG) — это и есть id
сообщения. Берите его из Reply для локальной отрисовки и для сверки с
событием доставки (`sys <cid> доставлено: <msg_id_hex32>`).
MockLink-паттерн store.next_msg_id в UdsLink НЕ используется.

### Q2. ts_ms — **ФОРМАТ: ставит ПРИЁМНИК, не отправитель**
`imsg <cid> <имя> <msg_id_hex32> <ts_ms> <текст>`: ts_ms — Unix epoch,
миллисекунды, UTC-основа, время ставит ядро ПРИЁМНИКА в момент приёма
(app.nowMs()). Группировка по локальному календарю получателя — верно.
Метка отправителя существует в конверте, но наружу не отдаётся
(приватность таймингов). Для ИСХОДЯЩИХ ts в стриме нет вообще — GUI
штампует локально в момент отправки (ts ядра для исходящего приходит
только через gethistory).
Реакции (`react`) тоже несут ts приёма — из getmessage.

### Q3. MsgId — **ФОРМАТ: 128 бит, hex32, не hex16/u64**
msg_id = [16]u8 CSPRNG (std.Io.random в engine.sendText). 128-битный
hex (32 символа). В u64 НЕ влезает. Между контактами не переиспользуются
(вероятность коллизии пренебрежима). Дедуп входящих делает ЯДРО (окно
последних 64 id на контакт) — в стрим дубликаты не попадают вовсе;
клиентский дедуп по id — защита от двойного чтения сокета, не от ядра.
**Действие GUI: расширить id-тип до hex32 (String/128 бит).**

### Q4. Порядок и дубли — **допущение верно, сильнее**
Внутри контакта — FIFO гарантируется (TCP + seq-счётчики кадров obf
+ ожидание строгого seq+1). События at-most-once: дедуп на 64-окне в
ядре. Офлайн-хвост после реконнекта доливается flushOutbox — тоже
идемпотентно (дедуп). Порядок исходящих подтверждается событием
`sys <cid> доставлено: <msg_id_hex32>` на каждое сообщение.

### Q5. Глобальные события — **допущение верно: событий без cid нет**
Все события (msg/imsg/sys/presence/call/avatar/file) несут cid.
Глобальных («демон поднялся/умер») в стриме НЕТ: смерть демона = EOF
UDS-сокета = LinkEvent::Down у вас. Это и есть канал «транспорт мёртв».
Фейк Sys в тред не нужен — мапьте на Down. Жизнь ОДНОГО контакта не
меняет стрим остальных.

### Q6. Семантика Down — **подтверждаю**
events() — один стрим на всё приложение; backoff/переподключение —
внутри UdsLink (новый UDS-коннект, каждая UDS-сессия получает полный
фан-аут событий заново — потерь между коннектами нет только для
ДОСТАВЛЕННЫХ сообщений; события между дисконнектом и реконнектом не
буферизуются — см. I-3 в вашем ISSUES). Down = «связи нет», стрим жив.
Повторный events() — контрактное нарушение, реализация вправе паниковать.

## Команды (Request → Reply)

### Q7. SendMsg офлайн — **ФОРМАТ: очередь, НЕ ошибка**
Допущение GUI НЕВЕРНО. Ядро кладёт в outbox: Reply успешен, строки
`msg_id <hex32>` + `в очереди: доставлю, когда <имя> появится`
(финал `@n ok`). Ретраев юзером не нужно — доставка автоматом при
следующей сессии, подтверждение событием `sys <cid> доставлено:`.
Это принцип ядра «максимум одно действие пользователя». Статус
доставки НЕ врёт: «отправлено в ядро» ≠ «доставлено» — различайте
локальный рендер и событие доставлено. (I-5 решается так: нет retry-UI.)

### Q8. Классы ошибок — **формат стабилен: `! <код>: <текст>`**
Строка ошибки начинается с `!` (финал `@n err`), формат:
`! not_found: не найдено`. Код — стабильный snake_case ASCII
(= Zig @errorName), текст — человекочитаемый, можно не показывать.
Реальные коды ядра:
```
bad_args          — неверные аргументы команды
no_contact        — cid вне списка контактов (unknown peer)
blocked           — контакт заблокирован (исходящие/реакции)
too_big           — тело > 4096 байт / файл > 64 МБ / имя > 32
bad_code          — инвайт-код не разобрался
too_many_invites  — > 4 живых инвайт-слотов
file_not_found    — путь sendfile/setavatar не читается
no_relay          — релей-диал не удался
no_session        — внутренние send-пути (обычно не наружу)
not_found         — getmessage: id нет в истории
bad_usage         — CLI-argc (не через UDS)
```
offline — НЕ ошибка (см. Q7). transport down — не командная ошибка
(Q6). Новые коды появятся с фичами — CHANGELOG обязателен.

### Q9. Block/Unblock — режет ОБА направления, пир уведомляется
- Исходящие: sendText/react на заблокированного → error blocked.
- Входящие: hard ignore в dispatch (конверты отбрасываются молча,
  пир не видит «доставлено»).
- Уведомление: BLOCK_NOTICE (0x14) уходит пиру, если он онлайн;
  у пира это событие sys-строкой в тред контакта. Локальная Sys-строка
  «заблокирован» — генерирует ЯДРО (fanoutSysLocked) в ваш стрим.
- Блок переживает рестарты (лог kind block).

### Q10. Инвайт — **v2, форма стабильна**
Канонический формат: `shopot://i/<base64url-nopad>@<host:port>`,
релей-вариант `@r/<host:port>`. base64url без паддинга, без пробелов.
Тело: bundle(64) || secret(16) || name_len u8 || имя(≤32).
v1 (`shopot1.`) — legacy, декодируется, не генерируется; «v2 shape»
мока совпадает с реальным. Срок жизни: до redemption (секрет
одноразовый), TTL НЕТ — известно ограничение, в ROADMAP. Слотов 4
одновременно. @-часть опциональна (LAN-поиск).

### Q11. Строка контактов — **ФОРМАТ: online|offline и 0|1, не on|off и b|-**
Точный формат (`contacts -m`):
```
c <cid> online|offline <0|1> <имя с пробелами>
c_end <n>
```
**Действие GUI: поменять парсер (on/off → online/offline, b/- → 0/1).**
Имя: ≤32 байтов UTF-8, пробелы допустимы, парсер = имя = всё после
третьего токена. Пустое имя невозможно (инвайты/setname требуют ≥1).
Переводы строк: через UDS-команды не вводятся (line-протокол рвёт по
\n); ядро не санитизирует — на всякий случай GUI рендерит имя как
плоский текст. cid — стабильный: = индекс в логе контактов (порядок
фиксирован, удаления контактов нет), переживает рестарты. Черновики
по cid осмысленны.

### Q12. Лимит сообщения — 4096 байт, Err, не обрезка
`max_text_body` = 4096 БАЙТ UTF-8 (не символов). Превышение —
`! too_big: ...` + `@n err`, обрезки нет. Композер GUI обязан
считать байты (не chars!). Реакции: codepoint ≤ U+10FFFF, на проводе
u32. История пишет только ≤4096 (больше всё равно не отправить).

### Q13. Отмена execute — отменяемо только ДО записи в сокет
UDS-транспорт: если future дропнут до записи — команда не уйдёт, честно
«не отправлено». Если запись уже произошла — ядро исполнит ВСЁ РАВНО
(команда в сокете; cancel-команды в протоколе нет). Отменённый future
после записи = «исход неизвестен»: сообщение может уйти. Утечек нет:
ответ придёт с тем же тегом @n — анрендеренный тег просто
выбрасывается. Рекомендация: не дропать future send-команд после
записи; для отмены UI — отменяйте до записи (модель mock «close
window» — только pre-write).

### Q14. Запуск демона (S5) — GUI спавнит, stderr забирает GUI
Рекомендация: GUI сам `spawn("shopot", ["serve"])` с HOME юзера.
Готовность: дем слушает UDS после инициализации; GUI поллит
connect() на `$HOME/.shopot/api.sock` (backoff 100мс→1с), затем
шлёт `@1 version` → `@1 core 0.5.0` — это проба и версии, и
живости (новая команда, добавлена в этом коммите). Смерть демона:
SIGCHLD (spawned вами) + EOF сокета → Down. stderr ядра: короткие
строки (startup, ошибки) — забирайте пайпом в лог GUI; формат строк
НЕ контракт, только диагностика. Права: сокет 0700, каталог ~/.shopot
0700 — запускать под тем же пользователем, что и GUI.
