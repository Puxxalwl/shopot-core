# CORE-API — интерфейс ядра shopot

Техническая спецификация для построения клиентов. Ядро (zig-демон `shopot serve`)
держит криптографию, контакты, сессии, доставку; клиент подключается по UDS и
рендерит. Формат — построчные UTF-8 строки, никакой структуризации поверх
(нет JSON). Каждый кадр — одна строка, окончание `\n`.

## 1. Модель

- **Ядро** — процесс `shopot serve`. Один пользователь = один демон = один
  $HOME. Несколько пользователей на машине — разные $HOME.
- **Клиент** — любое приложение (натив, TUI, сторожевой скрипт), подключается
  к $HOME/.shopot/api.sock (unix domain socket). Параллельно можно держать
  несколько клиентов; события рассылаются всем.
- **Контакт** — собеседник, идентифицируется bundle (enc_pk||sign_pk, 64 байта).
  В API контакт = целочисленный id (cid, стабильный на данном $HOME:
  1..N в порядке добавления).
- **msg_id** — 16 случайных байт, hex32 (64 hex-символа). Идентифицирует
  сообщение глобально; по нему реакция, статусы, getmessage.

### Принцип: максимум одно действие пользователя
Ядро берёт на себя: знакомство (JOIN-протокол), поиск адреса (LAN-мультикаст,
автодозвон), доставку офлайн (outbox+ACK), переподключение, presence. Для
пользователя любой сценарий = ноль или одно действие (вставить инвайт-код).
Клиент не должен просить подтверждений/адреса/порядка действий — всё уже
сделано ядром.

### Чего ядро НЕ делает
- UI/рендер/эмодзи-глифы, QR — клиент.
- Хранение на сторонних сервисах — их нет вообще; контент только на двух
  устройствах (шифрованный лог локален).
- NAT-обход для двух «за NATом» сторон: канал — LAN или прямой TCP
  (порты 7777-7786). Адрес для дальних — в инвайт-коде (@host:port).
- Разбор картинок/файлов: байты аватара (T4) передаются как есть, лимит
  на стороне ядра.

## 2. Подключение

```
socket = AF_UNIX, SOCK_STREAM
path   = $HOME/.shopot/api.sock
```

- Демон поднимает сокет при старте (`shopot serve`), удаляет при выходе.
- Одна строка = один кадр; длинные строки обрезаются по 2048 байт (max_line).
- Клиент держит соединение открытым: по нему приходят события (раздел 5).
- `quit` — закрыть соединение (не демон).

### Тег корреляции (рекомендуется всем клиентам)
Любая команда может нести префикс `@<n>` (`n` — цифры, уникальные в пределах
соединения):
```
@7 contacts -m
```
Тогда каждая строка ответа приходит с тем же префиксом `@7 ...`, а последняя —
`@7 ok` (успех) или `@7 err` (команда ответила строкой, начинающейся с `!`).
События ядра (msg/imsg/sys/presence/call) тегов НЕ несут никогда. Так роутер
клиента однозначно отличает ответы от событий и собирает многострочные ответы
(contacts, gethistory) по финальному `@n ok|err`.

## 3. Команды

Формат: `<команда> <аргументы...>\n`. Ответы — строки-строки ниже.
Все команды, кроме перечисленных в «не знаю команду», игнорируются
молча? нет — неизвестная команда отвечает `не знаю команду — /help для списка`.

### 3.1 Знакомство

#### `invite [имя] [addr]`
Создать одностороннее приглашение. Ответ:
```
shopot://i/<base64url(bundle|secret16|имя)>[@host:port]
односторонний код: отдай его — держатель сделает add, больше ничего не нужно
```
- имя (≤32 байт, по умолчанию `shopot`) — как держатель назовёт приглашающего.
- addr (опционально, `host:port`) — если известен; иначе держатель найдёт
  через LAN-анонс.
- секрет одноразовый: погашается первым валидным JOIN; реестр — до 4
  приглашений в памяти демона (после перезапуска код недействителен — выдай новый).
- Лимит: TooManyInvites при 4 непогашенных.

#### `add <код> [мое-имя]`
ЕДИНСТВЕННОЕ действие держателя кода. Ответы:
```
контакт <имя> = id <cid>
```
Дальше всё само: контакт, сессия, контакт у приглашающего (у него появится
`sys`-событие «контакт <имя> подключился по инвайту»), presence on.
- `мое-имя` (≤32 байта, default `друг`) — увидит приглашающий.
- Код с @addr — подключение немедленное; без — ждём LAN-анонс приглашающего
  (тот же WiFi) или его автодозвон.
- v1-коды (`shopot1.`) поддержаны — но требуют взаимного add.

#### `contacts` / `contacts -m`
Человеческий формат:
```
id <cid>: <имя> [online]|[offline] [ [BLOCKED]] (last seen: <мс> назад)[ [в очереди]]
```
Машиночитаемый (`-m`), по строке на контакт + финал:
```
c <cid> <online|offline> <blocked 0|1> <имя>
...
c_end <n>
```
Пустой список: `c_end 0` (или `нет контактов` без -m).

#### `id`
Свои публичные данные (сверка отпечатка голосом/QR):
```
bundle <hex128>          (enc_pk||sign_pk)
fingerprint <hex с пробелами>
```

### 3.2 Сообщения

#### `msg <cid> <текст>`
```
msg_id <hex32>
```
или (контакт офлайн):
```
в очереди: доставлю, когда <имя> появится
msg_id <hex32>
```
- тело ≤ 4096 байт UTF-8.
- Отправка офлайн НЕ ошибка: сообщение уйдёт при появлении контакта
  (outbox, доставка автоматическая, подтверждение — событие delivered).
- Текст с cid, которого нет — `! msg: <ошибка>`.

#### `gethistory <cid> [limit]`
Последние `limit` (default 50) сообщений переписки, старые→новые:
```
msg mine|theirs <msg_id_hex32> <ts_ms> <текст>
...
hist_end <cid> <всего_записей>
```
- `mine|theirs` — относительно владельца демона.
- ts_ms — локальное время записи в мс (epoch).
- Хранится в шифрованном логе; переживает перезапуски.

#### `getmessage <msg_id_hex32>`
```
msg mine|theirs <cid> <msg_id_hex32> <ts_ms> <текст>
react <mine|theirs> <codepoint> <ts_ms>     (по строке на реакцию)
```
или `! не найдено` (с тегом — финал `@n err`).

### 3.3 Реакции

#### `react <cid> <msg_id_hex32> <codepoint>`
Реакция на сообщение. codepoint — unicode code point, форматы ввода:
`10084`, `0x2764`, `U+2764`, либо сам глиф (`❤`). Диапазон ≤ U+10FFFF.
Ответ: подтверждения нет (тихо); ошибка — `! react: ...`.

Входящая реакция — событие (раздел 5, `react`).

### 3.4 Голый текст
Строка без известной команды = сообщение в «выбранный» чат. Рекомендация
клиентам: всегда явная форма `msg <cid> <текст>`; голый текст оставлен для
совместимости (выбранный контакт = первый в списке, sel по умолчанию 0).
Тег работает и здесь: `@5 привет` → ответ `@5 msg_id ...` / `@5 ok`.

### 3.4a Свой профиль

#### `setname <имя>`
Отображаемое имя (≤32 байта) — уходит пирам в PROFILE. Ответ: `имя задано`.

#### `setavatar <путь-к-файлу>`
Мой аватар: байты (≤16000, png/jpg — ядро не разбирает формат). Ответ:
```
аватар задан: <id_hex32> (<N> байт)
```
- id = SHA-256(данных)[0..16] — контент-адресация.
- Пиры онлайн получают PROFILE немедленно; офлайн — при следующей сессии.
- Хранение: шифрованный лог; переживает перезапуск.

#### `avatar <cid>`
Текущий avatar_id контакта: `avatar <id_hex32>` или `нет аватара`.
Сами байты приходят событием `avatar` (раздел 5) автоматически: ядро само
запрашивает их (AVATAR_REQ) при расхождении id и самоисцеляется при
реконнекте. Клиенту нужно только слушать событие и кэшировать по id.

### 3.4b Передача файлов

#### `sendfile <cid> <путь>`
Файл (≤64 МБ) уходит пир-у чанками по 16000 байт (каждый = один
obf-кадр). Ответ:
```
файл отправлен: <id_hex32> (<N> байт, <k> чанк.)
```
- id = SHA-256(файла)[0..16] — приём сверяет хэш и сохраняет в
  `~/.shopot/files/<id_hex32>` (0600). Дубликат (тот же id) не
  перекачивается — повторная отправка не тратит трафик.
- Событие у получателя: `sys <cid> file <cid> <id_hex32> <размер> <имя>`.
- Содержимое не сохраняется в истории; метка (kind FILE) — в логе.

### 3.5 Звонки

- `call <cid>` — предложить звонок (голос 16 кГц моно, E2EE, IMA-ADPCM
  4:1 на проводе = 72 кбит/с, DTX: тишина не шлётся кроме keepalive раз
  в 500 мс; см. PROTOCOL.md «Звонки»).
- `answer` — принять входящий.
- `hangup` — завершить/отклонить.
Машинные события (параллельно русским `sys`-строкам):
```
call <cid> offer|accept|reject|end <call_id_hex32>
```
`call_id` — общий идентификатор звонка; reject/end всегда завершают
аудиоконтур (после reject приходит и end).

### 3.6 Служебное

- `block <cid>` / `unblock <cid>` — блокировка (трафик дропается, пир
  предупреждается).
- `connect <addr:port> <cid>` — прямое подключение к контакту (обычно не
  нужно: ядро само).
- `help` — список команд.
- `quit` — закрыть соединение.

## 4. Модель доставки (важно для клиента)

1. `msg` при офлайне → outbox. Клиент показывает «отправится позже»
   (по ответу «в очереди»).
2. Контакт появился (LAN/автодозвон/вручную) → ядро шлёт очередь само.
3. Получатель подтверждает каждый TEXT конвертом ACK — отправителю прилетает
   событие delivered: клиент может показать галочку «доставлено».
4. Дубликаты невозможны: msg_id дедупится на приёме; повторная доставка
   после реконнекта идемпотентна.
5. Очередь переживает перезапуск демона (шифрованный лог), лимиты:
   1000 записей, TTL 30 дней.

Presence: онлайн = живое соединение; тишина > 4 с → PING/PONG; 3 пропуска
(5 с) → offline. События `presence <cid> on|off` приходят клиенту —
рендер статуса только по ним, не опрашивать.

## 5. События (демон → клиент)

Приходят ВСЕМ подключённым клиентам, в любом порядке:

| Строка | Значение |
|---|---|
| `msg <cid> <имя> <текст>` | входящее сообщение (legacy-формат) |
| `imsg <cid> <имя> <msg_id_hex32> <ts_ms> <текст>` | входящее сообщение с машинными полями (рекомендуемый формат) |
| `presence <cid> on\|off` | контакт на связи / пропал |
| `call <cid> offer\|accept\|reject\|end <call_id_hex32>` | перемена состояния звонка |
| `avatar <cid> <id_hex32>` | получены байты аватара контакта (sys-канал; кэшировать по id) |
| `sys <cid> file <cid> <id_hex32> <размер> <имя>` | принят файл целиком (байты в ~/.shopot/files) |
| `sys <cid> <текст>` | служебное: звонки, «контакт X подключился по инвайту», ниже — форматы |
| `sys <cid> доставлено: <msg_id_hex32>` | ваше сообщение дошло до устройства пир-а (ACK) |
| `sys <cid> react <msg_id_hex32> <codepoint>` | реакция на ваше сообщение |
| `sys <cid> входящий звонок — answer принять, hangup отклонить` | звонок |

ts_ms в `imsg` = локальное время приёма, совпадает с ts в gethistory
(метка в конверте TEXT остаётся приватной). msg_id входящего нужен для
реакций: `react <cid> <msg_id_hex32> <codepoint>`.

## 6. Сценарии (проверенные e2e)

### Добавление друга (один WiFi)
```
# сторона A (сын):
invite мама
# -> код; переслать любым мессенджером (только код, ноль контента)
# сторона B (мама):
add <код> мама
# далее: контакт у обоих, сессия сама, presence on, текст ходит
```

### Дальние (за NAT, но адрес известен)
A: `invite мама myhost.example.com:7777` → B: `add <код> имя`.
TCP-коннект B→A, всё остальное как выше.

### Офлайн-переписка
A пишет B-офлайн → «в очереди» → B запускает демон → ядро доставляет →
A: `доставлено: <msg_id>`.

### История при запуске клиента
`contacts` → для каждого cid `gethistory <cid> 50` → рендер.

## 7. Гарантии и границы

- Криптография: XX-подобное рукопожатие, AEAD-транспорт, рэтчет — см.
  PROTOCOL.md. Клиент НЕ касается ключей: сид в ~/.shopot/zig-seed (0600).
- Конкурентные клиенты: команды исполняются последовательно, события
  рассылаются всем; состояние (выбранный чат) — общее на демон.
- max_line = 2048 байт: длиннее — обрезка (тела сообщений до 4096 байт
  в событиях могут резаться — используйте gethistory для полных).
- Права: ~/.shopot — 0700, api.sock — 0700, zig-seed — 0600. Всё локально
  одному пользователю ОС.
- Джиттер-буфер звонка: кадры играются из очереди равномерно (~40-60 мс
  задержка), потери маскируются пропуском seq.
- Провод замаскирован под TLS 1.3 (fake-TLS): рукопожатие-имитация +
  записи application_data; пассивный DPI видит «обычный TLS» (см.
  PROTOCOL.md «Fake-TLS»). IP от пира скрыть нельзя (P2P) — для этого
  релей (ROADMAP P0).
- TCP_NODELAY на всех сокетах: интерактивные кадры без задержки Nagle.
- Сокет/файлы принадлежат $HOME; запуск нескольких демонов на одном $HOME
  не поддержан (один UDS-путь).
- Протокол версий не имеет: несовместимые изменения фиксируются в
  CHANGELOG.md и PROTOCOL.md.

## 8. Таблица конвертов (справка)

Полные раскладки байтов — PROTOCOL.md «Конверты». Клиенту достаточно знать:
TEXT (0x10) несёт msg_id/ts/тело; ACK (0x15) — подтверждение; REACT (0x13) —
op + unicode code point u32; JOIN (0x40) — доказательство по инвайт-коду;
PROFILE (0x42) — имя+avatar_id (эхо при каждом установлении сессии);
AVATAR/AVATAR_ACK/AVATAR_REQ (0x50/0x51/0x52) — передача аватаров;
CALL_SIGNAL/CALL_AUDIO — звонки; PING/PONG (0x20/0x21) — presence;
BLOCK_NOTICE (0x14) — блокировка. Клиент их НЕ строит — только ядро.
