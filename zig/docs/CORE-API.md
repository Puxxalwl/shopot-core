# CORE-API — бинарный интерфейс ядра shopot

Техническая спецификация для построения GUI-клиентов. Ядро (zig-демон
`shopot serve`) держит криптографию, контакты, сессии, доставку; клиент
подключается по UDS и рендерит. Протокол **бинарный**: никаких строк,
JSON и человекотекста на проводе — только типизированные байтовые кадры
и машинные коды (методы/статусы/события). Версия API: **1.0.0**.

## 1. Модель

- **Ядро** — процесс `shopot serve`. Один пользователь = один демон = один
  $HOME. Несколько пользователей на машине — разные $HOME.
- **Клиент (GUI)** — подключается к `$HOME/.shopot/api.sock`
  (unix domain socket, права 0700). Параллельно можно держать несколько
  соединений; события рассылаются всем.
- **Контакт** — собеседник, идентифицируется bundle (enc_pk||sign_pk,
  64 байта). В API контакт = целочисленный id (cid, u32, стабильный на
  данном $HOME: 1..N в порядке добавления).
- **msg_id** — 16 случайных байт. Идентифицирует сообщение глобально;
  по нему реакции, статусы, GET_MESSAGE.
- TUI/CLI у ядра нет: демон не имеет интерактивного ввода, всё управление
  идёт через это API.

### Принцип: максимум одно действие пользователя
Ядро берёт на себя: знакомство (JOIN-протокол), поиск адреса (LAN-мультикаст,
автодозвон), доставку офлайн (outbox+ACK), переподключение, presence. Для
пользователя любой сценарий = ноль или одно действие (вставить инвайт-код).
Клиент не должен просить подтверждений/адресов/порядка действий — всё уже
сделано ядром.

### Чего ядро НЕ делает
- UI/рендер/эмодзи-глифы, QR — клиент.
- Хранение на сторонних сервисах — их нет; контент только на двух
  устройствах (шифрованный лог локален).
- NAT-обход для двух «за NATом» сторон: канал — LAN, прямой TCP
  (порты 7777-7786) или релей (`shopot relay` на любом сервере).
- Разбор картинок/файлов: байты передаются как есть.

## 2. Кадр

Все числа — little-endian. Заголовок любого кадра — ровно 16 байт:

| Поле | Тип | Байты | Значение |
|---|---|---|---|
| magic | u16 | 0..2 | `0x5A50` («ZP») |
| version | u8 | 2 | `1` |
| kind | u8 | 3 | `1` = REQUEST, `2` = RESPONSE, `3` = EVENT |
| id | u16 | 4..6 | метод (REQUEST/RESPONSE) или событие (EVENT) |
| request_id | u32 | 6..10 | корреляция: клиент ставит, ядро повторяет в RESPONSE; у EVENT = 0 |
| status | u16 | 10..12 | код статуса (только RESPONSE; у остальных 0) |
| payload_len | u32 | 12..16 | длина payload, `0..1048576` (1 МиБ) |

- Один REQUEST = ровно один RESPONSE с тем же `id`/`request_id`.
- payload больше 1 МиБ — ядро отвечает `TOO_BIG` и рвёт соединение.
- Сломанная магия/версия или не-REQUEST кадр от клиента → `BAD_FRAME`,
  соединение закрывается (синхронизация потока не восстановима).
- Текстовых полей нет: строки — это «str16» = `[len u16][байты]` и
  «str32» = `[len u32][байты]` (сырые UTF-8 байты без терминатора).
- Лишние/недостающие байты в payload метода = `BAD_FRAME` (строгий разбор).
- CLOSE закрывает соединение (не демон).

## 3. Статусы (поле status кадра RESPONSE)

Имена — контракт; человекотекста в ответах нет и не будет.

| Код | Имя | Когда |
|---|---|---|
| 0 | `OK` | успех |
| 1 | `BAD_FRAME` | кадр/payload не разобран (магия, версия, длина, структура) |
| 2 | `UNKNOWN_METHOD` | неизвестный id метода |
| 3 | `BAD_ARGS` | неверные/неполные значения аргументов |
| 4 | `NO_CONTACT` | cid не существует |
| 5 | `CONTACT_BLOCKED` | контакт заблокирован локально |
| 6 | `NOT_FOUND` | объект не найден (сообщение по msg_id) |
| 7 | `TOO_BIG` | превышен лимит размера (тело, аватар, кадр, история) |
| 8 | `BAD_INVITE_CODE` | инвайт-код не разобран/не распознан |
| 9 | `TOO_MANY_INVITES` | реестр приглашений полон (4 живых) |
| 10 | `FILE_NOT_FOUND` | файл по пути не найден/не читается |
| 11 | `UNSUPPORTED_REACTION` | codepoint реакции вне U+0000..U+10FFFF |
| 12 | `NO_SESSION` | нет живой сессии с контактом (нужна для операции) |
| 13 | `BUSY` | линия занята (звонок уже идёт) |
| 14 | `NO_CALL` | активного звонка нет |
| 15 | `NO_RELAY` | релей недоступен |
| 16 | `TRANSPORT_FAILED` | транспорт не поднялся (dial/рукопожатие) |
| 255 | `INTERNAL` | внутренняя ошибка ядра |

## 4. Методы (REQUEST)

Имена — контракт, значения стабильны. «∅» — payload пустой.

### 4.1 Служебные

| Метод | id | Payload | Ответ (payload при OK) |
|---|---|---|---|
| `GET_VERSION` | 2 | ∅ | `[major u16][minor u16][patch u16]` |
| `GET_IDENTITY` | 3 | ∅ | `[bundle 64][fingerprint 32]` — отпечаток = BLAKE2s-256(bundle), сырые байты |
| `CLOSE` | 1 | ∅ | ∅, затем ядро закрывает соединение |

`GET_VERSION` — проба готовности: подключились → `GET_VERSION` → работаете.
Разрыв Major = контракт этого документа менялся (см. CHANGELOG).

### 4.2 Знакомство

#### `CREATE_INVITE` (4)
Payload: `[flags u8 (bit0 = relay)][name str16 ≤32][addr str16]`.
- name пустой → `shopot`; addr — `host:port` (опционально: иначе держатель
  найдёт через LAN-анонс); relay=1 → addr обязателен, подключение пойдёт
  через релей (пир не видит ваш IP).
- Секрет одноразовый: гасится первым валидным JOIN; реестр — до 4 живых
  приглашений в памяти демона (после перезапуска код недействителен).

Ответ: `[code str16]` — односторонний инвайт-код (URL `shopot://i/...`,
передаётся любым мессенджером; v1-коды `shopot1.` тоже принимаются).
Ошибки: `TOO_MANY_INVITES`, `BAD_ARGS`.

#### `ACCEPT_INVITE` (5)
Payload: `[code str16][my_name str16]`. ЕДИНСТВЕННОЕ действие держателя кода.
- my_name (≤32, пустой → `друг`) — увидит приглашающий.
- Код с адресом — подключение немедленное; без — ждём LAN-анонс/автодозвон.
- Статус подключения — по событиям `PRESENCE` (установка асинхронна).

Ответ: `[cid u32]`. Ошибки: `BAD_INVITE_CODE`, `BAD_ARGS`.

#### `LIST_CONTACTS` (6)
Payload: ∅. Ответ:
```
[count u32]
× { [cid u32][flags u8 (bit0 online, bit1 blocked)][last_seen_ms i64 (0 = неизвестно)][name str16] }
```

### 4.3 Сообщения

#### `SEND_MESSAGE` (7)
Payload: `[cid u32][body str16 ≤4096]`.
Ответ: `[msg_id 16][flags u8 (bit0 = queued)]`.
- Отправка офлайн НЕ ошибка: `queued=1` — уйдёт при появлении контакта
  (outbox, подтверждение — событие `MESSAGE_DELIVERED`).
- Ошибки: `NO_CONTACT`, `CONTACT_BLOCKED`, `BAD_ARGS` (пустое тело).

#### `SET_REACTION` (8) / `REMOVE_REACTION` (9)
Payload: `[cid u32][msg_id 16][codepoint u32]`.
- codepoint — Unicode code point, U+0000..U+10FFFF; вне диапазона —
  `UNSUPPORTED_REACTION`. Реакция требует живой сессии.
- Ответ: ∅. Ошибки: `NO_CONTACT`, `NO_SESSION`, `UNSUPPORTED_REACTION`,
  `CONTACT_BLOCKED`.
- Локальная история реакций фиксирует только постановки (снятие уходит
  пиру, в логе не отмечается — v1).

#### `GET_HISTORY` (10)
Payload: `[cid u32][limit u32]` (0 → 50; максимум 200 → `TOO_BIG`).
Ответ:
```
[total u32]   — всего записей у контакта
[count u32]
× { [flags u8 (bit0 mine, bit1 delivered)][msg_id 16][ts_ms u64][body str16] }
```
Записи старые → новые. ts_ms — локальное время записи (мс, epoch).
Хранится в шифрованном логе, переживает перезапуски. Лога нет — пустой
список (`total=0, count=0`).

#### `GET_MESSAGE` (11)
Payload: `[msg_id 16]`. Ответ:
```
[cid u32][flags u8 (bit0 mine, bit1 delivered)][ts_ms u64][body str16]
[react_count u32]
× { [flags u8 (bit0 mine)][codepoint u32][ts_ms u64] }
```
Нет записи — `NOT_FOUND`.

### 4.4 Свой профиль

#### `SET_NAME` (12)
Payload: `[name str16 1..32]`. Ответ: ∅. Уходит пирам в PROFILE (онлайн —
немедленно, офлайн — при следующей сессии).

#### `SET_AVATAR` (13)
Payload: `[data str32 1..16000]` — байты картинки inline (формат не
разбирается ядром). Ответ: `[avatar_id 16][size u32]`.
- avatar_id = SHA-256(data)[0..16] — контент-адресация.
- Хранение: шифрованный лог, переживает перезапуск.

#### `GET_AVATAR_ID` (14)
Payload: `[cid u32]`. Ответ: `[avatar_id 16]` (все нули — аватара нет).
Сами байты приходят событием `AVATAR_RECEIVED`: ядро само запрашивает их
(AVATAR_REQ) при расхождении id и самоисцеляется при реконнекте — клиенту
нужно только слушать событие и кэшировать по id.

### 4.5 Файлы

#### `SEND_FILE` (15)
Payload: `[cid u32][path str16]` — путь в ФС пользователя демона (клиент
кладёт файл, например, в `$HOME/.shopot/tmp/`, и передаёт путь).
- Лимит 64 МБ. Требует живой сессии (файлы не ставятся в outbox).
- Имя берётся из пути (basename, ≤64 байт).

Ответ: `[file_id 16][size u32][chunks u32]`.
- file_id = SHA-256(файла)[0..16]; приём сверяет хэш и сохраняет в
  `~/.shopot/files/<hex>` (0600). Дубликат не перекачивается.
- У получателя — событие `FILE_RECEIVED`.
- Ошибки: `NO_CONTACT`, `NO_SESSION`, `FILE_NOT_FOUND`, `TOO_BIG`, `BAD_ARGS`.

### 4.6 Звонки

| Метод | id | Payload | Ответ |
|---|---|---|---|
| `START_CALL` | 16 | `[cid u32]` | `[call_id 16]` |
| `ANSWER_CALL` | 17 | ∅ | ∅ |
| `END_CALL` | 18 | ∅ | ∅ |

- Голос 16 кГц моно, E2EE, IMA-ADPCM 4:1, DTX (см. PROTOCOL.md).
- Одна линия на демон: `START_CALL` при активном звонке → `BUSY`;
  `ANSWER/END` без звонка → `NO_CALL`. `START_CALL` без сессии → `NO_SESSION`.
- Аудио идёт через fifo `~/.shopot/pcm/mic|spk` (ядро читает/пишет).
- Состояния — события `CALL_STATE`.

### 4.7 Блокировка и транспорт

| Метод | id | Payload | Ответ |
|---|---|---|---|
| `BLOCK_CONTACT` | 19 | `[cid u32]` | ∅ |
| `UNBLOCK_CONTACT` | 20 | `[cid u32]` | ∅ |
| `CONNECT` | 21 | `[cid u32][addr str16]` | ∅ |
| `LISTEN` | 22 | `[addr str16][cid u32]` | ∅ |

`BLOCK_CONTACT`: трафик дропается, пир предупреждается. `CONNECT`/`LISTEN`
обычно не нужны (автодозвон/LAN сами); ошибки — `NO_CONTACT`,
`TRANSPORT_FAILED`, `NO_RELAY`.

## 5. События (EVENT)

Рассылаются всем подключённым клиентам, в любом порядке, request_id = 0.

| Имя | id | Payload |
|---|---|---|
| `MESSAGE_RECEIVED` | 1 | `[cid u32][msg_id 16][ts_ms u64][name str16][body str16]` |
| `MESSAGE_DELIVERED` | 2 | `[cid u32][msg_id 16]` |
| `PRESENCE` | 3 | `[cid u32][online u8 (1/0)][last_seen_ms i64]` |
| `REACTION` | 4 | `[cid u32][msg_id 16][op u8 (1 = add, 2 = remove)][codepoint u32][ts_ms u64]` |
| `CALL_STATE` | 5 | `[cid u32][call_id 16][state u8 (1 offer, 2 accept, 3 reject, 4 end)]` |
| `AVATAR_RECEIVED` | 6 | `[cid u32][avatar_id 16][data str16 ≤16000]` |
| `FILE_RECEIVED` | 7 | `[cid u32][file_id 16][size u32][name str16]` |
| `CONTACT_JOINED` | 8 | `[cid u32][name str16]` |
| `CONTACT_PROFILE` | 9 | `[cid u32][name str16][avatar_id 16]` |
| `BLOCKED_BY_PEER` | 10 | `[cid u32]` |

- `MESSAGE_RECEIVED.ts_ms` = локальное время приёма, совпадает с ts в
  GET_HISTORY. msg_id нужен для реакций.
- `PRESENCE` — рендер статуса только по нему, не опрашивать.
- `CALL_STATE`: reject/end всегда завершают аудиоконтур (после reject
  приходит и end).
- `CONTACT_JOINED` — держатель вашего инвайта подключился: контакт появился.
- `CONTACT_PROFILE` — имя/avatar_id контакта обновились (эхо PROFILE).

## 6. Модель доставки (важно для клиента)

1. `SEND_MESSAGE` при офлайне → ответ `queued=1`. GUI показывает
   «отправится позже».
2. Контакт появился (LAN/автодозвон) → ядро шлёт очередь само.
3. Получатель подтверждает каждый TEXT конвертом ACK — отправителю
   прилетает `MESSAGE_DELIVERED`: GUI показывает галочку «доставлено».
4. Дубликаты невозможны: msg_id дедупится на приёме.
5. Очередь переживает перезапуск демона (шифрованный лог), лимиты:
   1000 записей, TTL 30 дней.

Presence: онлайн = живое соединение; тишина > 4 с → PING/PONG; 3 пропуска
→ offline (`PRESENCE` с online=0).

## 7. Сценарии (в терминах API)

### Добавление друга (один WiFi)
```
A: CREATE_INVITE{name:"мама"}            → code
   (переслать код любым мессенджером)
B: ACCEPT_INVITE{code, my_name:"мама"}   → cid
   далее: сессия сама, PRESENCE online, текст ходит
A: слушает CONTACT_JOINED
```

### Дальние (за NAT, но адрес известен)
A: `CREATE_INVITE{name, addr:"host:7777"}` → B: `ACCEPT_INVITE`. Сокрытие
IP: A поднимает `shopot relay host:port` и делает `CREATE_INVITE` с relay=1.

### Офлайн-переписка
A пишет B-офлайн → `queued=1` → B запускает демон → ядро доставляет →
A: `MESSAGE_DELIVERED`.

### Старт GUI
connect → `GET_VERSION` → `LIST_CONTACTS` → для каждого cid
`GET_HISTORY{cid, 50}` → рендер; дальше всё по событиям.

## 8. Гарантии и границы

- Криптография: XX-подобное рукопожатие, AEAD-транспорт, рэтчет — см.
  PROTOCOL.md. Клиент НЕ касается ключей: сид в ~/.shopot/zig-seed (0600).
- Конкурентные клиенты: команды исполняются последовательно, события
  рассылаются всем.
- Права: ~/.shopot — 0700, api.sock — 0700, zig-seed — 0600. Всё локально
  одному пользователю ОС.
- Джиттер-буфер звонка: кадры играются из очереди равномерно (~40-60 мс
  задержка), потери маскируются пропуском seq.
- Провод замаскирован под TLS 1.3 (fake-TLS). IP от пира скрыть нельзя
  (P2P) — для этого релей (ROADMAP P0).
- Сокет/файлы принадлежат $HOME; запуск нескольких демонов на одном $HOME
  не поддержан (один UDS-путь).
- Версии API: Major меняется на несовместимых изменениях провода, Minor —
  на совместимых; фиксируется в CHANGELOG.

## 9. Таблица конвертов (справка)

Полные раскладки байтов — PROTOCOL.md «Конверты». Клиенту достаточно знать:
TEXT (0x10) несёт msg_id/ts/тело; ACK (0x15) — подтверждение; REACT (0x13) —
op + codepoint; JOIN (0x40) — доказательство по инвайт-коду; PROFILE (0x42) —
имя+avatar_id; AVATAR/AVATAR_ACK/AVATAR_REQ (0x50/0x51/0x52) — аватары;
FILE_META/FILE_DATA (0x60/0x61) — файлы; CALL_SIGNAL/CALL_AUDIO — звонки;
PING/PONG (0x20/0x21) — presence; BLOCK_NOTICE (0x14) — блокировка.
Клиент их НЕ строит — только ядро.
