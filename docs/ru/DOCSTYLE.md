# Правила написания документации

[English](../DOCSTYLE.md) | **Русский**

Обязательные правила написания и изменения документации в shopot-core.
Смоделированы с того, как Discord, Telegram, X, WhatsApp документируют
контракты для разработчиков, и как ядро Linux относится к документации как
к части патча. Нарушение — блокирующее на ревью, наравне со стилем кода.

## 1. Раскладка и языки

- **Английский — нормативная версия**, живёт в каноничном месте:
  `README.md`, `CONTRIBUTING.md`, `SECURITY.md` в корне; `zig/docs/X.md`
  для спецификаций.
- **Русские зеркала живут в каталогах `ru/`**: `docs/ru/README.md`,
  `docs/ru/CONTRIBUTING.md`, `zig/docs/ru/X.md` — то же имя файла, что у
  английского оригинала, без суффикса `.ru` (язык определяет каталог).
- Каждый док начинается строкой-переключателем языков со ссылкой на
  зеркало; работать должны оба направления.
- EN и RU не должны расходиться: изменение одного уезжает в другое **тем
  же коммитом**. Отставание перевода — баг.

## 2. Тон

- Нормативно и технически. Никакого маркетинга, воды, «просто»,
  «легко», восклицательных знаков.
- Только факты, настоящее время, активный залог. Доки описывают, что код
  делает сегодня — пожелания живут в ROADMAP.md и помечены как несделанные.
- Каждый док называет аудиторию в первых двух строках (авторы клиентов /
  контрибьюторы / разработчики ядра).

## 3. Факты — из кода

- Каждая байтовая раскладка, константа, лимит, числовой код и путь
  сверяются с исходниками до записи на бумагу. Никаких чисел по памяти.
- Код и доки расходятся → один из них неверен. Чините оба одним коммитом
  или заводите тикет; никогда не документируйте желаемое как текущее.
- Док не специфицирует поведение, которого нет в реализации (исключение —
  пункты ROADMAP, и они обязаны быть помечены).

## 4. Структура по типам доков

- **Спецификации** (PROTOCOL, CORE-API): нумерованные секции со
  стабильными номерами; существующие секции не перенумеровывать — только
  дописывать. Байтовые раскладки — в код-блоках; контракты — таблицами.
- **Машинные контракты** (статусы, методы, события, теги конвертов):
  таблица «числовое значение + имя SCREAMING_SNAKE + когда возникает».
  Имена — контракт; числа — провод.
- **Одна каноническая таблица лимитов на API-документ.** Новый лимит
  идёт туда, а не только в прозу.
- **Честные пределы**: каждый док про безопасность имеет секцию о том,
  что *не* покрыто (см. PROTOCOL §18).
- **Осознанные отклонения** от внешней спеки, на которую ссылаемся,
  оговариваются явно с причиной (например, капа размера аватара).
- Сценарии/quickstart описывают потоки в терминах API
  (запрос → ответ → событие), не прозой.

## 5. Нотация

- `u8`/`u16`/`u32`/`u64` — беззнаковые целые 1/2/4/8 байт.
  Little-endian по умолчанию; big-endian — только если поле это говорит.
- `[N]` — N сырых байт; `str16`/`str32` = `[len u16|u32][байты]` (UTF-8,
  без терминатора).
- Шестнадцатеричные константы с префиксом `0x`.
- Перенос прозы — не шире 80 колонок.
- Статусные символы (`✅`, `~~сделано~~`, `❌`) — только в ROADMAP.md.

## 6. Ссылки

- Относительные ссылки, резолвящиеся от директории самого файла. Перед
  коммитом прогоните проверку ссылок по изменённым файлам.
- Межъязыковые ссылки: EN → `ru/X.md`, RU → `../X.md`.
- Ссылаться на секции по номеру (`§7`), не только по заголовку.

## 7. Дисциплина изменений

- Изменение провода или API требует обновления соответствующего дока
  (PROTOCOL.md / CORE-API.md) **и записи в CHANGELOG.md тем же
  коммитом** — см. CONTRIBUTING §1 и §4.
- Строки версий внутри доков следуют версии провода/API; бампаются вместе
  с кодом.
- Новый документ регистрируется в таблице доков README (оба языка) и, если
  описывает процесс, ссылается из CONTRIBUTING.
- Перенос/переименование дока обновляет все входящие ссылки тем же
  коммитом.

## 8. Ревью

Доки ревьюятся по тому же чек-листу, что код: проверка ссылок, оба языка
обновлены, факты сверены с исходниками, запись в CHANGELOG при изменении
контракта. «Доки потом» — отказ.
