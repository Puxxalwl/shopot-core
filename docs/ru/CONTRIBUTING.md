# Контрибуция в shopot-core

[English](../../CONTRIBUTING.md) | **Русский**

Правила контрибуции смоделированы с процесса Linux kernel
([submitting-patches](https://docs.kernel.org/process/submitting-patches.html),
[submit-checklist](https://kernel.org/doc/html/latest/process/submit-checklist.html)),
адаптированы под Zig-проект на GitHub. Прочитайте до открытия PR.

## 1. Железные правила (инварианты — нарушения отклоняются)

- **Никаких серверов, телеметрии и сторонних вызовов** в ядре. Релей —
  софт, который хостит сам пользователь, а не сервис; LAN-поиск локален.
  Ничто в ядре не может требовать инфраструктуру.
- **std-only.** OS-пакеты (`pacman`/`apt`/`brew`) запрещены: пользователь
  не ставит ничего, кроме Zig. Zig-пакеты (build.zig.zon, фиксация хэшем)
  возможны, но каждая зависимость — с обоснованием в CHANGELOG.md; крипто-
  ядро остаётся на `std.crypto`.
- **Открытый текст не доходит до слоя диска.** Любой путь, пишущий
  пользовательский контент на диск, идёт через запечатанный лог. Тесты
  обязаны продолжать доказывать шифрование at-rest.
- **Никакого JSON на проводах.** Оба протокола (P2P и UDS) бинарные, LE,
  фиксированные ширины полей, без varint. Несовместимое изменение = бамп
  байта версии, не тихое переопределение поля.
- **Никаких новых криптопримитивов.** Только композиция std.crypto; ключи
  обнуляются `std.crypto.secureZero` при смерти владельца.

## 2. Окружение разработки

```bash
git clone https://github.com/Puxxalwl/shopot-core.git
cd shopot-core
make test                 # zig build test --summary all
make                      # zig build -Doptimize=ReleaseFast
```

Тулчейн: [Zig 0.17.0](https://ziglang.org/download/) — единственное
требование. CI гоняет тот же `zig build test` плюс релизные сборки на
каждом теге `zig-v*`.

Правила кода в дереве `zig/` (дисциплина аллокаторов, error-сеты, границы
модулей): [zig/AGENTS.md](zig/AGENTS.md). Они одинаково обязательны для
контрибьюторов и агентов.

## 3. Раскладка исходников и владение

| Подсистема | Файлы |
|---|---|
| build/интеграция | `build.zig`, `src/shopot.zig`, `src/shopot/core/*`, `src/shopot/app/*`, `docs/*`, `CHANGELOG.md` |
| crypto | `src/shopot/crypto/*.zig` |
| proto | `src/shopot/proto/*.zig` |
| net | `src/shopot/net/*.zig` |
| store | `src/shopot/store/*.zig` |

Изменение трогает файлы своей подсистемы; чужие подсистемы для автора
изменения только для чтения (интеграцию делает мейнтейнер root-скоупа).
Модуль импортирует только `core/interfaces.zig`, не соседей. Юнит-тесты
принадлежат владельцу модуля; интеграционные сценарии пишутся вместе с
интеграционным изменением.

## 4. Коммит-месседжи

Правила как в ядре, адаптированные:

- **Одно логическое изменение на коммит.** Коммит делает две вещи —
  разделите. Каждый коммит обязан собираться и проходить `zig build test`
  сам по себе (bisectability).
- **Subject**: `subsystem: summary в повелительном наклонении`, ≤ 72
  символов, без точки в конце. Существующие префиксы: `zig`, `zig: crypto`,
  `zig: net`, `zig: proto`, `zig: store`, `zig: app`, `zig: core`, `docs`.
  Если изменение чинит регрессию — в теле ссылка на коммит, который её
  внёс (аналог `Fixes: <12-hex>`).
- **Тело**: перенос на 72-й колонке. Описывайте, **что** делает изменение
  и **зачем** оно нужно — мотивация, влияние на threat-model для всего, что
  трогает крипту, хранилище или сигналинг. Построчное «как» — шум, diff
  уже это говорит.
- **Напишите, как тестировали** (добавленные юнит-тесты, интеграционный
  сценарий, E2E-прогон). «У меня работает» — не отчёт о тестировании.
- **Изменения крипты/протокола** дополнительно требуют: обновление
  `zig/docs/PROTOCOL.md`, запись в CHANGELOG.md и обоснование в теле
  коммита.
- Не смешивайте форматирование/переносы с функциональными изменениями;
  чистки `zig fmt` — отдельным коммитом (или, лучше, без них).
- Подписывайте каждый коммит:

```
Signed-off-by: Random J Developer <random@developer.example.org>
```

  Подпись удостоверяет [Developer Certificate of Origin
  (DCO)](https://developercertificate.org/): вы написали вклад сами или
  имеете право его присылать.

### Примеры

Хорошо:

```
zig: crypto: выводить AD sealed-кадра из полного заголовка

AEAD-бокс был привязан только к счётчику: замена байт префикса
длины давала валидный кадр, который приёмник разбирал неверно.
Привязать AD к [wirelen u16][seq u64], как obfuscate.zig уже
делает на пути записи.

Чинит регрессию, внесённую в 7b60347.

Тесты: юнит (roundtrip заголовка + tamper), интеграционный E2E 48 сообщений.
```

Плохо (отклоняется сразу): `fix`, `wip`, `update files`, subject > 72
символов, смесь fmt+логики, без тела, без подписи.

## 5. Чек-лист патча/PR

Адаптация kernel submit-checklist; сверьте каждый пункт:

- [ ] `zig fmt` не даёт diff (`zig fmt --check .`).
- [ ] `zig build test` зелёный.
- [ ] Новое поведение покрыто новыми тестами; баг-фикс содержит сначала
      падающий кейс.
- [ ] Нет `catch unreachable` вне тестов; нет `anyerror` на границах
      модулей; только модульные error-сеты.
- [ ] Публичные функции принимают `std.mem.Allocator`; нет аллокаций на
      горячем пути без комментирующего обоснования.
- [ ] Нет новых зависимостей — или сначала обоснование в CHANGELOG и
      обсуждение с мейнтейнером.
- [ ] Изменён провод — решение о байте версии принято явно, PROTOCOL.md
      обновлён.
- [ ] Тронут API — CORE-API.md обновлён, запись в CHANGELOG добавлена.
- [ ] Один смысл на PR; серия коммитов следует §4.
- [ ] Влияние на threat-model описано для изменений крипты/хранилища/
      сигналинга.
- [ ] Нет регрессий: E2E-сценарии в `tests/integration.zig` проходят
      без изменений.

## 6. Ревью и жизненный цикл

1. PR ревьюится по чек-листу выше. Правки форматирования/порядка аргументов
   могут доехать follow-up-коммитами; нарушения инвариантов (§1) закрывают
   PR.
2. Комментарии ревью закрываются в той же ветке — коммитом на пункт или
   squashed-фиксом со ссылкой. «Сделано» без изменения — не ответ.
3. Интеграцию (кросс-подсистемные мерджи, интеграционные тесты, релизы с
   тегами `zig-v*`) выполняет мейнтейнер root-скоупа.
4. Всё, видимое пользователю, попадает в CHANGELOG.md в момент мерджа,
   не позже.

## 7. Безопасность

Не открывайте публичные issues об уязвимостях. Следуйте
[SECURITY.md](SECURITY.md) (приватный GitHub security-репорт; цель —
подтверждение за 72 часа).
