# Политика безопасности

[English](SECURITY.md) | **Русский**

## Область действия

shopot-core защищает содержимое сообщений, файлы и локальную историю от
всех, кроме двух конечных точек. Точная граница — что покрыто, а что нет:
модель угроз в
[zig/docs/PROTOCOL.ru.md](zig/docs/PROTOCOL.ru.md#18-что-видит-наблюдатель).

## Репортинг об уязвимостях

**Не** открывайте публичные issues о проблемах безопасности.

- Откройте приватный репорт через вкладку GitHub *Security → Report a
  vulnerability* в репозитории, или
- свяжитесь с мейнтейнером по каналам из его GitHub-профиля.

Укажите: затронутый коммит, описание, proof-of-concept если возможно, и
ломает ли проблема конфиденциальность, целостность, аутентификацию или
доступность. Подтверждаем в течение 72 часов.

## Инвентаризация криптографии

| Примитив | Реализация | Для чего |
|---|---|---|
| X25519 | std.crypto | ключ шифрования личности, эфемерный ECDH, DH-шаги рэтчета |
| Ed25519 | std.crypto | подписи личности (аутентификация рукопожатия, привязка JOIN) |
| ChaCha20-Poly1305 | std.crypto | AEAD конвертов, кадров, записей at-rest, кадров звонка |
| Симметричный рэтчет | свой код на std HKDF/HMAC | ключи на сообщение (peek/commit по Double Ratchet spec §3.5) |
| DH-рэтчет (PCS) | свой код на std X25519/HKDF | ротация эпох каждые 256 отправленных сообщений: стороны обмениваются свежими X25519-пабликами (конверт RATCHET_KEY) и пересоздают цепочки совместным DH-шагом |
| HKDF-SHA256 | std.crypto.kdf | всё выводение ключей |
| HMAC-SHA256 | std.crypto | шаг цепочек рэтчета, marker-ы релея, доказательства JOIN |
| BLAKE2s-256 / SHA-256 | std.crypto | отпечатки, хэш транскрипта, контент-адресация (файлы, аватары), целостность |

Рукопожатие дополнительно сверяет статический X25519-ключ из m2/m3 с
известным bundle контакта (KeyMismatch закрывает соединение) — практика
noise-libp2p: remote static проверяется приложением после XX.

Правила дизайна, enforcing на ревью:

- Никаких самодельных примитивов — только композиция std.crypto.
- Нонсы из счётчиков: повтор пары (key, nonce) невозможен по построению.
- Ключи сообщений используются ровно один раз и обнуляются.
- Приёмная цепочка сдвигается только после успешной расшифровки.
- Секреты личности/рэтчета/хранилища обнуляются `secureZero` при смерти
  владеющих объектов.
- Провалы аутентификации роняют кадры молча, без оракульного поведения.

## Заметки по харденингу для разработчиков клиентов

- Файл сида — это личность: держите `~/.shopot/zig-seed` (0600) вне любых
  бэкапов/синков, которые сами не E2EE. У кого сид — у того и история.
- Просите пользователей сверять отпечатки при добавлении контактов
  (защита от MITM на первом контакте).
- Храните сид на общих устройствах только с дополнительной защитой
  (пароль поверх — забота клиента; ядро выводит всё из сырого сида).
- Паника/удаление: уничтожение `~/.shopot` (сид, лог, файлы) стирает
  историю, outbox, файлы и контакты. Личность (сид) выживает by design —
  удалите и `zig-seed`, если умереть должна сама личность.
